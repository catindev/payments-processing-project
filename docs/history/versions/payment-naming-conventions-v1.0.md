# NAME-01 — именование полей контрактов и базы данных

**Статус:** согласовано заказчиком 2026-10-09. **Применение:** все новые собственные публичные API, внутренние интерфейсы, события, JSON-схемы, DTO, колонки БД и конфигурации, являющиеся нашим контрактом.

## Правило

1. **Предпочтительно одно смысловое слово, максимум два.** Запись собственных JSON/SQL-полей — `snake_case`. При наличии контекста сущности не дублировать её имя в поле.
2. Если одного слова хватает без двусмысленности, оно обязательно предпочтительнее двух. Например `reduce`, `paid`, `status`, `attempts.used`, `amounts.paid`. Вложенные объекты помогают сократить названия.
3. **Два слова разрешены, если одно непонятно или неоднозначно**: `intent_id`, `amount_final`, `method_type`, `order_id`, `policy_revision`. Слова `id`, `ref`, `at`, `count` учитываются как смысловые части имени.
4. Не использовать искусственные сокращения, вырванные из контекста, вроде `camtr` или `stcp`. Лаконичность не должна снижать точность названий и провоцировать путаницу boolean/amount/id.
5. **Полный смысл поля — в спецификации**, включая: единицы суммы (копейки), правила null, значения, тип, источник истины, алгоритм записи, запреты и пример.
6. Не менять имена, требуемые внешними банковскими протоколами. При переводе через адаптер банк по-прежнему видит `ExtId`, `CardRefID`, `TCB-Header-Sign` и аналогичные имена. У нас используется короткое нормализованное поле.
7. Для ранее подготовленного, но ещё не опубликованного API применяем сокращение сразу в следующей черновой версии. Для уже опубликованного API потребовались бы версионирование и миграция — такое применение не было предметом этого согласования.
8. **Инвариант CI:** имя *собственного поля* с третьим сегментом, разделённым `_`, не проходит линтер. При изменении схемы БД проверяются колонки отдельно. Имена enum-значений, type alias, SQL-таблиц и маршрутов проверяются отдельно и не считаются полями; для них краткость также рекомендуется.

## Примеры

| Было в черновике | Стало | Контекст |
|---|---|---|
| `confirm_amount_reduction` | `reduce` | Boolean запроса `CaptureRequest` для дочернего Payment |
| `payment_intent_id` | `intent_id` | Поле `Payment`, внешний ключ БД |
| `saved_payment_method_id` | `method_id` | ID сохранённого способа оплаты в `Payment` |
| `payment_method_id` | `method_id` | ID способа оплаты в setup/session |
| `payment_method_type` | `method_type` | Тип способа оплаты в `Payment` |
| `latest_payment_id` | `last_payment` | ID последнего дочернего Payment у Intent |
| `successful_payment_id` | `paid_payment` | ID успешного дочернего Payment у Intent |
| `multiple_partial_captures` | `multi_capture` | Флаг функциональности в публичном `MethodCapability` |
| `save_for_future_use` | `save` | Режим сохранения способа оплаты, enum on_session/off_session |
| `merchant_connection_id` | `connection_id` | Собственный внутренний SPI |
| `provider_request_reference` | `request_ref` | Внутренний correlation ID команды |
| `original_provider_reference` | `original_ref` | ID исходной банковской операции |
| `provider_operation_reference` | `operation_ref` | ID последней банковской операции, если есть |

`amount_final` оставлено в двух словах намеренно: `final` само по себе не отличает сумму от признака финальности. `amount_paid` также сохраняется как две понятные части.

## Данные и банк

- У `PaymentIntent` собственные поля: `id`, `amount`, `amount_final`, `amount_paid`, `status`, `attempts`, `expires_at`, `paid_payment`.
- У `Payment` ссылка `intent_id`, а не `payment_intent_id`; у банковского адаптера своя ссылка `operation_ref` и исходный `original_ref`.
- У физической колонки, представляющей внешний ID исходной операции банка, выбирайте, например, `original_ref`, но только при очевидности таблицы и контекста. Если контекст недостаточен, вынесите смысл в имя таблицы или отдельную сущность, **не в три слова поля**.
- Сырые банковские JSON и журнал полученных сообщений хранят имена провайдера дословно и **не** проходят преобразование имён; это отдельный слой данных.

## Проверки и ограничения

- Проверка `components.schemas.properties` OpenAPI и полей собственного интерфейса TypeScript — в `check-payment-names-v1.py`.
- В репозитории реализации аналогичную проверку требуется включить в CI для моделей БД и SQL-миграций; сейчас реальных миграций нет. Приведённая норма не подтверждает выбранную СУБД.
- Имеющийся исследовательский `tkb-connector-profile-v0.3.yaml` содержит технические многословные диагностические ключи/коды и **не объявляется приведённым к NAME-01**: этот профиль подлежит отдельной нормализации при переходе от исследовательского материала к реализации. Разработчики не должны копировать эти старые ключи в публичный API.
