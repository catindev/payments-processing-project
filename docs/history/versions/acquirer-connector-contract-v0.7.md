# Контракт банковского соединителя — проект v0.7

**Дата:** 2026-10-09  
**Статус:** на техническое согласование. Нельзя считать подтверждением возможностей ТКБ.  
**Связанные материалы:** `payment-lifecycle-spec-v0.8.md`, `payment-api-v0.8.openapi.yaml`, `acquirer-connector-v0.5.ts`, `acquirer-connector-contract-tests-v0.7.yaml`, `tkb-connector-profile-v0.3.yaml`.  
**Секреты:** документы содержат только условные идентификаторы. Кредитные данные из Postman не копировались; к стенду ТКБ запросы не выполнялись.

## 1. Статус требований и ограничения

- **[Б] Согласовано заказчиком:** единый публичный API для юрлиц, ИП и физлиц на НПД; приём денег за собственные товары/услуги; единое дистанционное подключение клиентов; несколько банков; первый стенд — ТКБ; не менее 100 RPS публичного интерфейса.
- **[Б] Согласовано BR-01, BR-02, BR-02.1, BR-03.1, BR-03.2 и BR-04:** самостоятельный `Payment`, необязательный управляющий `PaymentIntent` над последовательными отдельными платежами; новый `Payment` только по действию покупателя, без автоматических повторов.
- **[П] Проект технического контракта:** `PaymentOperation`, `Refund`, `PaymentMethod`, `AcquirerConnection`, `DispatchIntent`, API v0.8 и описываемый здесь интерфейс соединителя.
- **[И] Подтверждено из переданной коллекции ТКБ:** есть примеры регистрации оплаты, создания холда, подтверждения/отмены холда, возврата, получения статуса, СБП QR, привязки карт. Отдельные примеры Postman **не подтверждают** доступность функции для нашей учётной записи, финальность состояния, безопасные повторы или договорные полномочия платёжного агрегатора.
- **[О] Открыто:** BR-05—BR-06 жизненного цикла, конкретные антифрод-правила и приоритет конкурирующих причин закрытия; политика финальности по конкретным банкам; подтверждённый срок действия холда; гарантии идемпотентности ТКБ; формат достоверных уведомлений; перечень функций каждого торгового терминала.

**Принцип:** банк исполняет команды, а процессинг управляет их безопасной постановкой, состоянием, суммами, историей и правами продавца. Соединитель не является владельцем финансового учёта. **Банковский соединитель не принимает, не создаёт и не подтверждает `PaymentIntent`; это исключительно роль ядра.**

## 2. Область ответственности

| Платёжное ядро (core) | Банковский соединитель (adapter) |
|---|---|
| Публичный API, авторизация продавца и его права | Реальный банковский адрес и транспорт |
| Выбор маршрута и разрешённых платежных инструментов | Преобразование команды в запрос конкретного банка |
| Создание самостоятельного `Payment`, банковских операций и связей с необязательным `PaymentIntent` | Преобразование ответа в нормализованный результат |
| Атомарные резервы сумм, версии объектов, идемпотентность клиента | Подпись исходящего запроса, проверка подлинности ответа/уведомления |
| Сохранение действий до отправки, журнал отправок | Документированные технические возможности и ограничения провайдера |
| Алгоритм восстановления при `unknown` | Запрос состояния, если банк его поддерживает |
| Финансовый журнал, сверка и отчёты продавца | Получение/разбор банковских реестров, если доступно |
| Проверка порядка событий, разрешение конфликтов | Преобразование исходных банковских кодов и событий, без самовольного изменения сумм |

Ни один банк не определяет внутренние имена `Payment.status` и `PaymentIntent.status` и не может произвольно изменять правила расчёта `refundable` или `capturable`.

## 3. Типизированный программный интерфейс

Нормативный для обсуждения исходный вариант: [`acquirer-connector-v0.5.ts`](acquirer-connector-v0.5.ts). Его функция — зафиксировать **семантику**, а не предписать использование TypeScript для реализации процессинга.

```ts
interface AcquirerConnector {
  readonly provider: string;
  getCapabilities(ctx: AcquirerContext): Promise<CapabilityProfile>;
  submit(ctx: AcquirerContext, command: ConnectorCommand): Promise<ConnectorResult>;
  lookup(ctx: AcquirerContext, query: LookupOperation): Promise<LookupResult>;
  verifyAndParseNotification(ctx: AcquirerContext, raw: RawBankNotification): Promise<BankNotificationResult>;
  getSettlementRecords?(ctx: AcquirerContext, cursor: SettlementCursor): Promise<readonly SettlementRecord[]>;
}
```

Команды: `debit`, `authorize`, `capture`, `void`, `refund`, `setup_method`, `debit_saved`.

### 3.1. Уточнения технического поведения (сохранены в проекте жизненного цикла v0.8)

1. `debit` — единое прямое списание (одностадийная карта или обычная оплата СБП). **Не** нужно создавать фиктивную пару `authorize`/`capture` ради унификации.
2. Если `capture` или `void` однозначно **не выполнены**, банк подтвердил отсутствие эффекта и исходный холд продолжает действовать, `Payment` может вернуться из `processing` в `requires_capture`; `PaymentOperation.status=failed`, сумма освобождается из внутреннего резерва. Если холд истёк, требуется отдельное подтверждение его исхода.
3. Если `capture` мог выполниться, но итог не установлен, восстановление `requires_capture` и повторный `capture` **запрещены**.
4. Финальный `Payment.status=succeeded` после частичного capture возможен только после достоверного положительного результата по правилам конкретного банка, включая разрешение остатка холда.
5. Для `PaymentOperation` публичный статус — `processing | pending | succeeded | failed | reversed`; внутренние `created | submitted | unknown` сохраняются, а наружу отражаются через `processing.reason`.

Эти уточнения присутствуют в проекте жизненного цикла v0.8; технические правила требуют отдельной проверки. BR-01, BR-02 и BR-02.1 являются согласованными бизнес-решениями.

### 3.3. BR-03.1 — одно окончательное списание холда [Б / П]

**[Б] Согласовано:** в первом выпуске — одна успешно завершённая окончательная команда `capture` на одну авторизацию, с полной или частичной суммой. Несколько успешных списаний — расширение и в публичном выпуске v1 выключено.

**[П] Технические следствия:**

- В базовом выпуске ядро отправляет соединителю `capture.final=true`; публичное поле `final_capture` удалено. Любой запрос с таким полем отклоняется до банка по строгой схеме даже при поддержке многократных списаний банком.
- Частичное списание допускается только при подтверждённой возможности конкретного `connection_id`; отсутствие поддержки нельзя обходить `capture(вся сумма)` + `refund(разница)`.
- Внутренний журнал допускает несколько команд `capture` только если все предыдущие финансово **доказанно безрезультатны** и исходный холд продолжает действовать. Не более одной успешно завершённой окончательной операции. `unknown`/`pending` блокируют дальнейшие изменения холда.
- Банковский ответ об успешном списании части суммы и факт освобождения остатка — логически разные утверждения. В профиле соединителя нужно определить доказательства списания и правило освобождения; при неопределённости не объявлять остаток свободным на основании разницы `authorized-captured`.
- `multi_capture` остаётся описываемой возможностью банка и расширением будущего продукта, но в v1 не превращается в доступную функцию для продавца.

**Внешняя зависимость:** наличие в примере ТКБ пути `/api/v1/card/unregistered/hold/confirm/partial` подтверждает форму запроса с суммой, но не права терминала и не окончательность банковского результата. Следует проверить на стенде только после согласования тестового сценария.

## 4. Идентичность и корреляция

| Поле | Чья сущность | Назначение |
|---|---|---|
| `payment_id` | Наша | Один самостоятельный жизненный цикл оплаты через выбранный банковский маршрут |
| `intent_id` (необязательное) | Наша | Корреляция с верхним намерением, **не** часть бизнес-контракта с банком; может не передаваться соединителю |
| `operation_id` | Наша | Один финансовый эффект: debit, authorize, capture, void, refund |
| `command_id` | Наша | Одна неизменная подготовленная команда на отправку |
| `request_ref` | Наша/банк | Заранее назначенная внешняя ссылка, только если протокол допускает передачу |
| `original_ref` | Банк | Идентификатор исходного банковского платежа/холда для следующих действий |
| `payment_ref` | Банк | Присвоенный банком ID платежа, если возвращается |
| `operation_ref` | Банк | Присвоенный банком ID **данной** операции, если отличается от платежа |
| `connection_id` | Наша | Привязка конкретного продавца к банковскому терминалу и его полномочиям |

Один `ExtId` ТКБ в `RegisterOrderFromUnregisteredCard` создаёт исходную операцию, но в примерах `Refund`, `Reverse`, `HoldConfirm` этот параметр используется для **обращения к исходной операции**. Не следует автоматически трактовать его как уникальный ID нового возврата/подтверждения. Внутренний `operation_id` всегда уникален; отдельный банковский reference может отсутствовать — это важная причина осторожности с автоматическими повторами.

`request_ref` назначается и сохраняется **до** возможной отправки. Если команда финансово опасна и банк не гарантирует её идемпотентность, новый `command_id` или новая строка в базе не являются разрешением повторить её по сети.

## 5. Результаты выполнения

`ConnectorResult.kind` принимает следующие значения.

| Значение | Что известно | Действие ядра |
|---|---|---|
| `requires_action` | Нужна банковская форма, 3DS, QR либо переход в приложение | Сохранить `Payment` и `next_action`; не считать платёж оплаченным |
| `accepted` | Банк признал команду принятой, финансовый результат не окончателен | `pending`, ждать события или допустимого запроса состояния |
| `succeeded` | Доказан эффект `paid / authorized / captured / voided / refunded / method_saved` | Провести один подтверждённый финансовый факт, проверить ограничения |
| `reversed` | Доказано обращение ранее подтверждённого возврата (финансовое обратное событие) | По одному свидетельству создать компенсирующий факт, привести `Refund` в `reversed`, уведомить продавца; при противоречии открыть сверку |
| `declined` | Доказан отказ **без** финансового эффекта | `Payment.failed` окончательно; если есть `PaymentIntent`, ядро может разрешить **новый** дочерний `Payment` по действию покупателя |
| `unknown` | После возможной отправки итог не выяснен; сеть/HTTP не дают доказательств | Сохранить резерв, **не** менять банк/не отправлять повтор без гарантии |
| `not_dispatched` | Достоверно доказано, что команда не могла достичь банка | Разрешить исправление/безопасный повтор после перепроверки |

Обязательные доказательства для `succeeded` и `declined`: `ResultEvidence` с локальным `evidence_id`, источником (`authenticated_http_response`, `verified_callback`, `status_query`, `reconciliation_report`, `manual_bank_confirmation`), внешней ссылкой и версией правила преобразования (`rule_version`).

**Важно:** даже аутентифицированный ответ с кодом `OK` может означать **только принятие команды**. Переводить его в `succeeded` можно лишь после проверки точной семантики конкретного банковского метода. Аналогично `not_found` при запросе статуса не обязательно является доказательством «списания не было».

### 5.1. Доказательство финальности

Для каждой пары `(провайдер, операция)` в профиле должно быть согласовано, какое сообщение достаточное: синхронное подтверждение, проверенный ответ статуса, уведомление, реестр, письменное подтверждение банка. Если такой критерий не определён, возвращать `accepted`/`unknown`, **не** `succeeded`.

Поздние корректировки банки могут присылать даже после положительного подтверждения. Они учитываются новым фактом (`reversed` / correction), а не редактированием старой записи журнала.

## 6. Безопасная отправка и восстановление

### 6.1. Подготовка команды

В одной транзакции хранилища ядра: проверить права продавца, состояние платежа, выбранное подключение и банковские возможности, отсутствие конфликтующего `unknown`, лимит суммы, уникальность `Idempotency-Key` и (для дочерней оплаты) атомарную блокировку `PaymentIntent`; затем сохранить `PaymentOperation`, внутренний резерв суммы, неизменный внешний reference и запись **намерения отправки** (`DispatchIntent`).

### 6.2. Передача банку

Исполнитель берёт `DispatchIntent`, сохраняет состояние `dispatch_started` **до потенциальной отправки** и передаёт команду соединителю. Если исполнитель упал между записью `dispatch_started` и подтверждённым ответом, нельзя доказать, был ли сетевой вызов. Это `unknown`, пока не получено дополнительное доказательство.

**Нельзя обеспечить «ровно один вызов банка» одной транзакцией нашей базы данных.** Можно обеспечить один локальный ресурс и безопасный процесс восстановления; отсутствие повторного финансового эффекта требует подтверждённой идемпотентности банка или достоверного выяснения результата.

### 6.3. Восстановление

1. Найти исходный `command_id`, неизменяемый маршрут и заранее выделенную внешнюю ссылку.
2. Проверить сохранённые ответы/проверенные уведомления.
3. Выполнить `lookup` по **исходному** банку и допустимому интервалу (для ТКБ: в образце Postman оговорён минимум 60 секунд между запросами к одной операции; подтвердить договорно).
4. Если банк говорит `not_found` без гарантии окончательности — оставить `unknown`.
5. Повторную отправку разрешить только при документально подтверждённой идемпотентности для **данного** метода и ключа, либо если достоверно доказано отсутствие предыдущей отправки.
6. При противоречивых свидетельствах создать инцидент сверки и заблокировать рискованные действия.
7. После подтверждения обновить финансовый журнал и снимок `Payment` атомарно, выдать событие продавцу.

**Сценарий отказа канала связи:** магазин повторяет API с тем же `Idempotency-Key`. Ядро возвращает один исходный ресурс; для `PaymentIntent.confirm` сохраняется **тот же дочерний `Payment`**. Новый запрос в банк при этом необязателен и может быть запрещён.

**BR-01 + BR-02:** если внешний банк вернул доказанный окончательный отказ, `Payment.failed` терминален. Следующую оплату создаёт ядро как новый `Payment` по новому вызову `PaymentIntent.confirm` (при действии покупателя) либо продавец напрямую через `POST /payments`. Соединитель не создаёт повторов самостоятельно и не переключает банк после финансового отказа. Ядро также запрещает создание новых дочерних оплат после наступления срока, предела попыток, запроса отмены продавцом или блокировки по рискам. Финальный неуспешный `PaymentIntent` возможен только после исключения незавершённого финансового эффекта; банк не знает ни `expires_at`, ни счётчик попыток намерения.

### 6.4. BR-02.1 — границы ответственности за срок, попытки и риск [Б / П]

- **[Б]** Для нового `PaymentIntent`: срок по умолчанию 30 минут (5 минут — 24 часа), лимит по умолчанию 5 (1–10), неизменный снимок настроек на момент создания. Это **политика ядра**, а не новый метод или обязанность банка.
- **[Б]** Три уровня раскрытия причин риска: покупатель — нейтральное сообщение, продавец — категория/ссылка поддержки, сотрудник с полномочиями — детали. Соединитель не раскрывает внутренние признаки риска и не формирует пользовательские тексты.
- **[П]** Ядро атомарно проверяет срок и доступный лимит при создании дочернего `Payment` и перед потенциальной отправкой. Соединитель независимо исполняет фактические ограничения банковской формы/QR/холда. Не передавать `intent.expires_at` как банковский TTL без явной политики преобразования.
- **[П]** Банк может подтвердить операцию после истечения окна новых попыток; это учитывается в финансовом журнале. Пока исход не доказан, новый дочерний платёж и финальное отрицательное состояние не разрешены.

### 6.5. BR-04 — окончательность возврата [Б / П]

**[Б] Согласовано:** `Refund.succeeded` только при документально достаточном подтверждении банковского **исполнения**, не при HTTP 200/202, `accepted` или регистрации заявки. Время видимого зачисления у покупателя не требуется для этого статуса; клиенту нельзя обещать мгновенное поступление. Прямой `Payment` и дочерний `Payment` сохраняют `succeeded` после возврата.

**[П] Требования к соединителю:**

1. Для каждого `(provider, connection_id, операция refund, версия профиля/правила)` перечислить источники и коды, при которых ответ означает `accepted` (ожидание), `succeeded` (исполнено), `declined` (доказан отказ), `unknown` (неясен эффект) или `reversed` (поздний доказанный обратный эффект). Не применять правила `debit`, `capture` или `void` к `refund` по сходству названий.
2. Факт исполнения привязать к конкретным `refund_id`, `operation_id`, исходному `payment_id`, сумме, валюте и банковской корреляции. Если банк возвращает только исходный `ExtId` и нельзя отличить несколько частичных возвратов, **не** угадывать исход операции.
3. При `accepted` ядро сохраняет `pending`, при `unknown` — `processing`, сумма остаётся зарезервированной. `succeeded` переносит резерв в подтверждённую нетто-сумму `refunded`; доказанный `declined` снимает резерв.
4. `reversed` является отдельным нормализованным результатом **после** доказанного успеха. Сверить сумму обратного движения, создать неизменяемый корректирующий факт, применить его только один раз и уведомить продавца. Противоречивый `declined` после `succeeded` без доказательства финансового обращения — инцидент, не перезапись состояния.
5. Одинаковый callback/ответ/реестровый факт не влияет на суммы дважды. Не повторять refund по `timeout`, `5xx`, неопределённому статусу или новому ключу клиента без доказанной безопасности банковского повтора.
6. Для ручного подтверждения необходимо **подтверждение банка**, ссылка на документ/операцию, версия правила и сотрудник/время в аудите. Решение оператора без банковского свидетельства не является достаточным основанием успеха.
7. Банковский вывод финальности является **непроверенной внешней зависимостью**, пока не утверждены таблицы статусов и способ сверки по данному терминалу. При отсутствии способа выяснения результата **не активировать возврат** по этому банковскому маршруту.

**ТКБ [И]:** документированный `/api/v1/card/unregistered/debit/refund` принимает `ExtId` исходного платежа и `amount`, его описание — «регистрирует заявку»; документация из коллекции не доказывает статус финального исполненного возврата, отдельный банковский ID возврата или гарантии повторов. Политика маппинга для ТКБ по-прежнему `unverified`, тестовые операции в банк не отправлялись.

## 7. Контроль сумм

Все суммы внутри ядра и соединителя: целые копейки (`RUB`); десятичные дроби и плавающие вычисления денег не допускаются. В TypeScript `MoneyMinor=number` сопровождается проверкой `Number.isSafeInteger(value)` и пределов; для хранения поддерживается точный целочисленный тип. Для иной валюты потребуется отдельная спецификация масштаба.

- `paid <= requested`; нет конвертации и увеличения итоговой суммы без отдельного бизнес-правила.
- `refunded + refund_reserved <= paid` при обычных возвратах; резервы обособлены от подтверждённого результата.
- `capture_reserved` защищает от параллельных `capture` и `void` по одному холду.
- `authorized, captured, paid, released` — разные показатели. Для обычной СБП `paid > 0`, но `captured = 0`.
- Результат банка может менять доступные суммы только после проверки относимости к конкретным `payment_id/operation_id` и зафиксированной банковской корреляции. `PaymentIntent` меняет только производное состояние.
- Возврат не меняет исторический `Payment.status=succeeded`, а меняет `amounts.refunded` после проверенного результата.

## 8. Поддержка возможностей банка

`CapabilityEvidence.status` — **три значения**: `supported`, `unsupported`, `unknown`. Неизвестность не равна «банк не умеет», но для выбора маршрута и рекламы функции продавцу приравнивается к *недоступно до подтверждения*.

| Возможность | Пример ограничения |
|---|---|
| `manual_capture` | Поддержка терминалом и методом оплаты |
| `single_partial_capture` | Механизм судьбы остатка холда |
| `multi_capture` | Явная поддержка банка/договора; по умолчанию недоступно |
| `partial_refund`, `multiple_refunds` | Максимальная сумма, количество и окно возврата |
| `setup_card`, `merchant_initiated_saved_payment` | Согласие плательщика, применимый токен, терминал/банк |
| `sbp_dynamic_qr` | Срок жизни QR и подтверждение оплаты |
| `status_by_reference` | Допустимая частота опроса и точность ответа |
| `provider_idempotent_replay` | Гарантия именно для конкретной команды, reference и срока |
| `signed_callbacks` | Действительный механизм аутентификации событий |
| `reconciliation_feed` | Доступные отчёты и банковские доказательства |

**Профиль может различаться для двух продавцов одного банка.** Сохранять версию профиля в `Payment` и `PaymentOperation`, чтобы после изменения настроек не переписывать объяснение старых решений.

## 9. Специфика банка в JSONB/BSON

Публичные ресурсы не содержат `provider_data`. Внутри ядра — только проверяемые и версионируемые данные в отдельной области банка. Конкретная база хранения пока не выбиралась: PostgreSQL `jsonb` либо BSON в документной БД.

Пример **вымышленного**, неплатёжного контекста:

```json
{
  "provider": "tkb",
  "schema_version": 1,
  "data": {
    "payment_ref": "tkb_payment_example",
    "status_code": "EXAMPLE_PENDING",
    "form_flow": "hosted_card_form",
    "document_version": "unconfirmed"
  }
}
```

- Только соединитель `tkb` может записывать/интерпретировать `data` своей версии. Изменение схемы требует миграции или совместимого чтения старых версий.
- Запрещено хранить там PAN, CVV/CVC, секреты подписи, персональные документы, токены с прямым доступом к операциям без защиты. Ссылки на защищённые токены — отдельная область.
- Настройки, входные данные, ответ и техническое свидетельство — **разные документы**, а не один бесконтрольный `raw_json`.
- Банковские коды не превращаются автоматически в новые публичные состояния; для неизвестного кода — `unknown` и инцидент/уточнение.
- JSON Schema банковского расширения и правила преобразования привязаны к `config_version` и `rule_version`; при диагностике сохраняем их значения.

## 10. Профиль ТКБ — подтверждённое и открытое

См. машиночитаемую матрицу [`tkb-connector-profile-v0.3.yaml`](tkb-connector-profile-v0.3.yaml).

| Наше действие | В коллекции TKB PAY | Вывод / ограничение |
|---|---|---|
| `debit` новая карта | `/api/v1/card/unregistered/debit`, `RegisterOrderFromUnregisteredCard` | В примере `ExtId` — новая операция; есть `Amount`, `Description`; финансовые статусы требуют проверки |
| `authorize` | `/api/v1/card/unregistered/hold/register` | Есть регистрация холда; терминальные права/TTL неизвестны |
| `capture` | `/api/v1/card/unregistered/hold/confirm/partial` | `ExtId` и `amount`; название `partial` **не доказывает** многократное подтверждение |
| `void` | `/api/v1/card/unregistered/hold/reversal/partial` | `ExtID` и `Amount`; окончательная семантика отмены требует проверки |
| `refund` | `/api/v1/card/unregistered/debit/refund` | `ExtId` идентифицирует *исходную* операцию, `amount` — сумму возврата; отдельный банковский ID возврата не доказан |
| `debit` через СБП | `/api/v1/sbp/register/qrc` | В примере только динамический QR (`Static=false`), `ExpirationMinutes` указан, но это не гарантия фактического TTL |
| `debit_saved` | `/api/v1/card/registered/direct` | `CardRefID` относится к TKB PAY; переносимость в другой банк неизвестна |
| `lookup` | `/api/v1/order/state` | В примере `ExtID`; комментарий — не опрашивать одну операцию чаще минуты |
| `verifyAndParseNotification` | Упомянут `Callback Service` в приложенной документации | Доказательство подлинности, формат и порядок событий не приложены в достаточной мере |
| `setup_method` | `/api/v1/card/unregistered/bind` | Есть метод; статус результата привязки/согласия и конкретные права терминала — вопросы |

**Не пытаться осуществлять эквайринг на банковском стенде от имени не одобренного агрегатора.** Технический доступ к `paytest` не подтверждает заключённых договоров для привлечения третьих продавцов.

## 11. Общая проверка подключения другого банка

Добавление банка Б **не** должно менять схему `Payment`, денежные единицы, трактовку `unknown`, гарантию одного положительного результата или набор публичных состояний. Меняются `AcquirerConnector`, `CapabilityProfile`, нормализация событий, правила доказательств и `ProviderParameters`.

Новый банк принимается только при наличии достаточных сведений для: исходящей оплаты; безопасного определения исхода; возвратов/отмен; возможности конкретного продавца; безопасности уведомлений; отчётности и ручной сверки при неопределённости. Опциональные функции не должны блокировать базовые платежи другого банка.

## 13. Уточнения, для которых нужны документы банка (а не догадки)

1. Выдаёт ли ТКБ для каждого `Refund`/`HoldConfirm` отдельный уникальный банковский ID? Как отличить два частичных возврата с тем же исходным `ExtId` после потери ответа?
2. Имеет ли повтор одной финансовой команды с прежним `ExtId` доказанную идемпотентность? Каковы срок хранения ID, область уникальности и поведение на несовпадение суммы?
3. Какое значение `GetOrderState` подтверждает, что операция действительно не была создана, а какое означает «ещё не найдена»?
4. Какие состояния callback являются окончательными для платежа, capture, refund и обычной СБП? Чем подтверждаются подписанность/подлинность событий?
5. Можно ли делать несколько частичных `HoldConfirm` или `Refund` для одного исходного `ExtId`? Что происходит с неиспользованным остатком холда?
6. Какая схема регистрации и подключения отдельных продавцов предусмотрена для агрегатора; допускаются ли физлица на НПД? Какие права выделяются отдельному терминалу?
7. Какие сверочные файлы/реестры доступны для финансовых инцидентов? Как сопоставлять запись реестра с нашим `operation_id`?
8. Какие банковские предельные значения по RPS, размеру платежа и интервалам запросов состояния установлены для наших ключей?

## 16. BR-03.2 и NAME-01: подтверждение снижения и краткие поля

**BR-03.2 согласовано.** Только ядро проверяет явное `reduce=true` при окончательном частичном capture дочернего Payment. Банковскому соединителю отправляется сумма финансового `capture` и внутренний признак `final=true`; его контракт не управляет `PaymentIntent.amount_final`.

Успешный банковский capture не даёт права заранее объявить остаток холда освобождённым без подтверждённой семантики конкретного банка; сведения о закрытии холда обрабатываются процессингом как доказательства. Если результат ещё неизвестен — сохраняется processing, новое финансовое действие запрещено.

**NAME-01:** собственные поля SPI и модели БД сокращены до одного-двух смысловых слов (`connection_id`, `request_ref`, `original_ref`, `operation_ref`, `method_id`). Нормативное руководство — `payment-naming-conventions-v1.1.md`. Значения (`ExtId`, заголовки, поля банковского JSON) внешних протоколов не переименовываем. Справочные строковые коды банковских возможностей и исходов требуют отдельной проверки совместимости при обновлении профилей, не являются подтверждёнными идентификаторами продавца.
