# Проект платёжного процессинга — аналитическая модель v0.8

Дата: 2026-10-09  
Статус: **BR-01, BR-02, BR-02.1, BR-03.1, BR-03.2, BR-04, BR-05 и NAME-01 согласованы; BR-06 и детали архитектуры остаются проектными.**  
Основа: предоставленная документация TKB PAY, официальные API Stripe, Adyen, ЮKassa, Т-Банка, Сбера и Альфа-Банка.

> Безопасность: в этом документе нет адресов закрытых банковских стендов, ключей, номеров карт или учётных данных. Коллекция Postman с учётными данными не должна попадать в репозиторий.

## 1. Входные бизнес-требования

**Подтверждено заказчиком:**

- Одна платёжная компания подключает юридические лица, ИП и физических лиц на НПД.
- Клиент принимает платежи за **собственные** товары или услуги; маркетплейсные распределения и выплаты третьим лицам не входят в начальный объём.
- Клиент подключается самостоятельно через единый кабинет без самостоятельных интеграций с банками.
- Один и тот же публичный платёжный API должен работать с несколькими банками и способами оплаты: карты, СБП, кошельки.
- Требуются: создание и получение платежа, полные и частичные возвраты, холдирование и подтверждение, привязка карт и повторные списания.
- Ориентир производительности: не менее 100 запросов в секунду на публичном API; это **не** означает подтверждённую пропускную способность каждого банка.
- Первый доступный партнёр для исследований — тестовый контур ТКБ. Правовая модель окончательно не утверждена; прямые расчёты банка с продавцом — текущая рабочая гипотеза.

Важно: `extId` — идентификатор операции у клиента ТКБ, `OrderId` — внутренний идентификатор TKB PAY. Наличие уникального `extId` **не доказывает автоматически идемпотентность любых финансовых вызовов**. Проверить семантику отдельно.

Также встречаются AFT, P2P, переводы, управление картами ТКБ и банковскими счетами. Это не части стартового продукта интернет-эквайринга; не экспортировать их автоматически.

**Угроза в коллекции:** в значительной части подготовительных скриптов Postman выводится секретный ключ в `console.log`. Удалить такие строки и заменить тестовый ключ.

## 4. Основные проектные принципы

1. **[Б] Независимые `Payment` и необязательный `PaymentIntent`.** Продавец может работать напрямую с отдельными платежами; управляемое намерение связывает последовательные отдельные платежи. После доказанного отказа — новый `Payment`, но только по действию покупателя внутри намерения. Нет автоматического переключения банков.
2. **Операция не равна результату.** Ответ `200` на создание возврата может означать лишь принятие заявки. Храним жизненный цикл каждого `Capture`, `Refund`, `Void` независимо.
3. **Читатель получает сохранённое внутреннее состояние, а не прямой вызов банка.** Обновление через callback, ограниченный опрос и сверку.
4. **Данные, важные для денежных обязательств, типизированы.** Нельзя держать суммы, статусы и привязки исключительно внутри произвольного BSON/JSON.
5. **Банковские детали изолированы.** Публичный API не требует банковских терминалов, EAN, `extId` ТКБ и т.д.
6. **Единая интеграция с клиентом, отдельные разрешения по банкам.** Доступный способ оплаты определяется конкретной активной банковской связью торговой точки и возможностями разрешённого терминала.
7. **Распределённая обработка не означает распределённые транзакции с банком.** Отправки и ответы записываются с восстановлением после обрывов соединения.

## 5. Предлагаемый публичный API `/v1`

| Метод | Ресурс | Назначение |
|---|---|---|
| `POST` | `/payments` | Создать независимый платёж; `confirm: true` — инициировать сразу |
| `POST` | `/payment_intents` | Создать управляемое намерение для одной покупки |
| `GET` | `/payment_intents/{intentId}` | Состояние намерения и ссылки на успешный/последний платёж |
| `POST` | `/payment_intents/{intentId}/confirm` | По действию покупателя создать и инициировать новый дочерний `Payment` |
| `POST` | `/payment_intents/{intentId}/cancel` | Отменить намерение безопасным образом |
| `GET` | `/payment_intents/{intentId}/payments` | История дочерних самостоятельных платежей |
| `GET` | `/payments/{paymentId}` | Текущее сохранённое состояние и суммы |
| `GET` | `/payments` | Список с фильтрами по заказу, периоду, состоянию |
| `POST` | `/payments/{paymentId}/confirm` | Только первая инициация ранее созданного платежа; повтор оплаты после отказа запрещён |
| `POST` | `/payments/{paymentId}/capture` | Подтвердить полный или частичный холд |
| `POST` | `/payments/{paymentId}/cancel` | Отменить не завершённый платёж или авторизацию, если позволяет банк |
| `POST` | `/refunds` | Новый полный или частичный возврат по `payment_id` |
| `GET` | `/refunds/{refundId}` | Состояние отдельного возврата |
| `GET` | `/payments/{paymentId}/operations` | История финансовых операций (без банковских секретов) |
| `POST` | `/customers` | Покупатель в пределах конкретного магазина |
| `POST` | `/setup_sessions` | Инициировать сохранение карты без покупки |
| `GET` | `/setup_sessions/{setupId}` | Результат привязки/подтверждения |
| `GET` | `/payment_methods` | Сохранённые методы конкретного покупателя |
| `DELETE` | `/payment_methods/{paymentMethodId}` | Отключить дальнейшее использование |
| `GET` | `/capabilities` | Доступные магазину способы, функции и ограничения |
| `POST` | `/webhook_endpoints` | Настроить URL клиентских уведомлений |

На этой стадии **не** включаем публичные `payouts`, `transfers`, `split`, `balances` и прямые банковские методы. Фискализацию проектируем отдельной предметной областью с возможностью ссылаться на платёж.

### Конвенции

- `Authorization: Bearer <api_key>` — клиентский серверный ключ, с ограниченными правами и привязкой к магазину.
- `Idempotency-Key` обязателен для изменяющих финансовое состояние `POST`: уникален в пределах клиента, действия и ресурса. Повтор с прежним телом даёт тот же ресурс; повтор с другим телом — `409`. Новый `PaymentIntent.confirm` после отказа требует **нового ключа** и явного действия покупателя.
- Суммы целочисленные в младших единицах валюты: `amount=125000`, `currency=RUB` означает 1 250 рублей (вариант BR-06 **ещё не согласован**). Никогда `float`.
- Не доверять `merchant_id`, переданному в теле: определять продавца из авторизованного контекста. `outlet_id` опционален для нескольких торговых площадок одного продавца.
- `metadata` — ограниченные произвольные данные самого магазина, не содержащие карточных реквизитов и чувствительных сведений.
- Не передавать полный номер карты, CVC/CVV, банковские HMAC-ключи и данные пользовательской авторизации в публичный API. Платёжные формы и токенизацию проводит сертифицированный провайдер/банк.
- `return_url` — адрес возврата браузера; факт успешности оплаты определяем через `GET`/подписанный webhook, не по открытию этого URL. Возвратные адреса проверять по разрешённым доменам.
- Ответы на создание/изменение могут иметь промежуточное состояние `processing` и HTTP 202; это не отказ и не подтверждённый успех.

Для управляемой оплаты магазин сначала создаёт `PaymentIntent` и затем вызывает
`POST /v1/payment_intents/{intentId}/confirm` по действию покупателя. В ответе

## 6. Два жизненных цикла [Б / П]

**[Б] `Payment`:** отдельный платёж. Если банк достоверно отказал без списания — `failed` и никаких следующих попыток внутри него; при банковской неопределённости — `processing` и уточнение. Остальные состояния: `requires_payment_method` (только до первой отправки), `requires_confirmation`, `requires_action`, `requires_capture`, `succeeded`, `canceled`, `expired`. Возвраты не меняют исторический `succeeded`.

**[Б] `PaymentIntent`:** необязательная надстройка, один заказ и сумма; собирает несколько последовательных дочерних платежей и их историю. После окончательного отказа дочернего платежа возвращается в `requires_payment_method` (пока не сработала согласованная политика закрытия BR-02). При успехе ребёнка — `succeeded`. При финальном частичном capture отдельно показывается `amount_paid < amount` и нельзя считать заказ полностью оплаченным без проверки суммы (проект; обсудить в BR-03). При активном/неизвестном исходе дочернего платежа новая оплата **запрещена**.

**[Б] Повтор только по действию покупателя:** `POST /payment_intents/{id}/confirm` должен инициироваться после выбора/подтверждения покупателем нового способа оплаты. В первом выпуске нет автоматических повторов или выбора другого банка после отказа. Прямой клиент сам создаёт новый независимый `Payment`.

**[П] Достоверность:** атомарно запрещать несколько одновременно активных детей одного намерения, фиксировать отдельные финансовые операции и банковские идентификаторы. Не объявлять абсолютную гарантию на случай, когда банк позднее изменяет уже подтверждённый отказ. Такой конфликт требует финансового инцидента.

### 6.1. Границы параметров `PaymentIntent` и доступа к риск-данным [Б / П]

- **[Б]** Для нового намерения действует исходная политика продавца: `ttl_seconds=1800` (границы 300–86400) и `max_attempts=5` (границы 1–10). Индивидуальная настройка продавца и согласованный разовый `expires_at` проверяются при создании; готовый Intent получает неизменный снимок.
- **[Б]** Новые попытки прекращаются после истечения окна, исчерпания попыток, отмены или блокировки. Исход уже созданного банковского платежа не определяется этими часами и счётчиками.
- **[Б]** Уровни раскрытия риска: плательщику только нейтральное сообщение, продавцу общая категория с ссылкой поддержки, полномочным сотрудникам — полный защищённый журнал.
- **[П]** Хранить снимок лимитов и версию политики вместе с Intent, а журналы антифрода — отдельно с ограничением доступа. Настройка профиля продавца через кабинет и проектный API `/v1/payment_intent_settings` не должны задним числом менять живые Intent.
- **[П]** Проверка окна, лимита и активного дочернего Payment должна быть атомарной; защиту от обхода лимитов созданием множества Intent нужно проектировать отдельно как общую антифрод-политику.

## 7. Предлагаемые основные сущности

| Сущность | Назначение / существенные поля |
|---|---|
| `Merchant` | ЮЛ/ИП/НПД, юридические данные, подключение |
| `Outlet` | Торговая площадка продавца |
| `AcquirerConnection` | Банк, торговый терминал, права, поддерживаемые способы и ограничения |
| `Customer` | Покупатель в пределах продавца |
| `PaymentIntent` | Необязательная управляемая покупка: `id`, `order_id`, сумма, валюта, ограничения, активный/успешный дочерний платёж |
| `Payment` | Самостоятельный платёж: `id`, `intent_id` (nullable), сумма, валюта, состояние, суммы операций, выбранное подключение |
| `PaymentOperation` | `debit`, `authorize`, `capture`, `void`, `refund`; отдельные банковские команды и факты |
| `Refund` | Независимая публичная сущность возврата конкретного `Payment` |
| `PaymentMethod`, `ProviderToken` | Сохранённый способ и банковский токен с областью использования |
| `IdempotencyRecord` | Ключ, тип команды, ресурс, отпечаток тела, выданный результат |
| `ProviderEvent`, `WebhookDelivery` | Входящие события банка и события продавцу |
| `SettlementRecord`, `ReconciliationCase` | Перечисления продавцам и разбирательства расхождений |

Связь `Payment` с `PaymentIntent` устанавливается один раз только при создании процессингом дочернего платежа и не может изменяться. **Обязательной предметной сущности `PaymentAttempt` нет.** Внутренние транспортные попытки банковских команд могут сохраняться в техническом журнале без дополнительного публичного ресурса.

Это логические сущности, не список отдельных микросервисов.

## 8. Слой банковских соединителей

Для обсуждения принят единый интерфейс `AcquirerConnector` из [`acquirer-connector-v0.5.ts`](acquirer-connector-v0.5.ts): `getCapabilities`, `submit`, `lookup`, `verifyAndParseNotification` и дополнительный `getSettlementRecords`. Внутренние команды: `debit`, `authorize`, `capture`, `void`, `refund`, `setup_method`, `debit_saved`.

Банковский соединитель видит **один конкретный `Payment` и его `PaymentOperation`**, но не управляет `PaymentIntent`, повторными покупками или маршрутизацией после отказа. `intent_id` остаётся корреляцией для ядра и уведомлений. Банк не определяет публичные состояния намерения.

Результаты различают `requires_action`, `accepted`, `succeeded`, `declined`, `unknown`, `not_dispatched`, каждый с подтверждаемой семантикой. Сетевой тайм-аут и HTTP 5xx после возможной отправки не являются доказательством отказа.

Банковская конфигурация включает карту статусов/ошибок, ограничения на запросы, поддерживаемые функции, схему безопасности и сценарии сверки. Подробности — в `acquirer-connector-contract-v0.2.md`.

### 8.1. BR-04 — ответственность ядра за возвраты [Б / П]

- **[Б]** `Refund` относится к самостоятельному `Payment`, включая дочерние платежи намерения. HTTP 200/202, принятие заявки или присвоение банковского идентификатора не подтверждают исполнение. `succeeded` — результат достаточного банковского финансового доказательства. Подтверждение отображения денег на счёте покупателя не требуется.
- **[П]** Ядро владеет `Refund.status`, внутренним резервом, нетто-учётом `refunded`, идемпотентностью запросов, финансовым журналом и исходящими событиями `refund.succeeded|failed|reversed`. Банк через соединитель поставляет только проверенные свидетельства, не определяет финансовую модель.
- **[П]** `pending` — подтверждён приём заявки, `processing` — отправка/неизвестность. В обоих случаях деньги зарезервированы от второго возврата. При подтверждении исполнения резерв переносится в учтённый возврат. При доказанном отказе резерв снимается.
- **[П]** Позднее обращение ранее успешного возврата — новый компенсирующий факт (без редактирования старого журнала), `Refund.reversed`, повторный подсчёт чистой суммы и уведомление продавца. Нельзя автоматически отправлять ещё один возврат.
- **[П]** У каждого результата хранится доказательство и корреляция с конкретным refund, исходной оплатой, суммой, валютой, банком и версией правил. При недостатке достоверных данных — `processing`/сверка, а не выдуманный успех. Поздние противоречивые сообщения без доказательства обращения — инцидент.
- **[Б]** Исходные `Payment` и `PaymentIntent` остаются исторически `succeeded` после полного или частичного возврата. Покупателю не обещаем момент зачисления; юридический момент исполнения обязательства решается отдельно.

### 8.2. BR-05 — координация отмены и позднего результата [Б / П]

**[Б] Утверждено:** продавец может запросить отмену, но факт успешного банковского списания после такого запроса остаётся успешным `Payment` и `PaymentIntent`. Отмена отмечается отдельным отказом и уведомляет продавца; создание `Refund` автоматом запрещено в v1. `Refund` создаётся отдельным запросом продавца при необходимости. Предусмотренная на будущее возможность `refund: true` пока не доступна.

**[П] Компоненты:**

- **Payment core:** атомарно фиксирует намерение отмены и запрет создания новых дочерних платежей/конфликтующих команд. Если команда уже достигла банка, хранит исходное состояние и выясняет результат.
- **Cancel coordinator:** логическая функция ядра, не обязательно отдельный микросервис. Поддерживает отдельный статус `cancel` и коррелирует команду `void`/выяснение дебета с исходным Payment. При позднем успехе устанавливает `cancel.failed`, не превращая оплаченное в `canceled`.
- **Acquirer connector:** даёт `lookup`, результаты реальной банковской отмены холда и допустимого `reverse` при подтверждённом контракте. Не создаёт Refund и не принимает решения об отмене товара или заказа.
- **Events/outbox:** после атомарной фиксации позднего успеха отправляет `payment.cancel_failed` или `payment_intent.cancel_failed`; обязательны `event_id`, подпись, повторная доставка без смены event ID и устойчивое хранение.
- **Reconciliation:** при подтверждении успеха уже после доказанного `canceled` фиксирует противоречие как инцидент; исторический терминальный факт не перезаписывается без разбирательства.

Инвариант: один запрос отмены с прежним `Idempotency-Key` не создаёт второй финансовой команды; наличие нескольких банков не разрешает перенос неопределённого исхода на другой маршрут. Все выводы о поведении TKB `Reverse`/`HoldReversal` требуют реальной проверки.

## 9. Расширяемые данные: JSONB или BSON

Для этих требований **не предлагаю хранить весь `Payment` в BSON**. Важные суммы, статусы, ссылки и ключи должны иметь явную схему, индексы, ограничения и транзакционную целостность.

Предложение для первой реализации: реляционное хранилище, например PostgreSQL, с полями `jsonb` (двоичный JSON). `BSON` нужен, если будет выбрана MongoDB или другой продукт, который его использует. Выбор формата JSONB/BSON — реализация, а не бизнес-требование.

Гибкие документы уместны для:

1. `AcquirerConnection.configuration` — несекретная конфигурация банка и торговой точки;
2. `Payment.provider_data` — идентификаторы и дополнительные сведения самостоятельного банковского платежа;
3. `PaymentOperation.provider_data` — ответ/состояние конкретного подтверждения, отмены или возврата;
4. `ProviderEvent.payload` — ограниченная по сроку, проверенная и очищенная копия входящего события;
5. `CapabilityProfile.parameters` — лимиты и возможность операций по действующему договору.

**Пример внутреннего документа (не внешний API):**

```json
{
  "provider": "tkb",
  "schema_version": 1,
  "connection_id": "acq_0123",
  "references": {
    "operation_ref": "attempt-8932",
    "order_ref": "bank-example-431"
  },
  "context": {
    "form_flow": "bank_hosted",
    "raw_state": "BANK_SPECIFIC_CODE"
  },
  "extensions": {
    "tkb": {
      "callback_profile": "default"
    }
  }
}
```

Значения демонстрационные, это **не** фактический банковский ответ.

### Обязательные ограничения расширений

- `provider` + `schema_version`; проверка через JSON Schema, миграции между версиями.
- Публичный `metadata` (данные магазина) и внутренний `provider_data` — разные поля с разными правами доступа.
- В `provider_data` не допускаются PAN, CVC, секреты, токены доступа, исходные неподтверждённые подписи и необработанные персональные данные.
- Для конфиденциальных, но допустимых технических данных — шифрование, ограничение чтения и срока хранения; ключи и учётные данные только во внешнем хранилище секретов.
- Нельзя передавать произвольную конфигурацию напрямую в банковский запрос из API клиента: допускаются только явно описанные `method_options` и разрешённые схемой параметры.
- Для поиска и сверки отдельно индексировать `provider`, `order_ref`, `merchant_id`, `payment_id`, `intent_id`, `operation_id` в обычных столбцах.

## 10. Маршрутизация и токены

**Правила выбора банка:**

- доступность по договору для конкретного продавца и категории деятельности;
- поддержка конкретного платёжного инструмента и режима операции;
- ограничения по валюте, сумме, стране, MCC, условиям повторной оплаты;
- техническая доступность, ограничения частоты запросов и тарифы;
- фиксировать выбранный банк на уровне конкретного `Payment` после начала банковского сеанса.

**Запрещённое автоматическое поведение:** при тайм-ауте создания платежа в банке A нельзя создать новый дочерний `Payment` в банке B, пока не исключён финансовый эффект первого платежа. После доказанного отказа новый ребёнок создаётся только по действию покупателя.

Банковские токены рассматриваются как чувствительные платёжные реквизиты: хранение в зашифрованном виде с отдельным контролем доступа, без публикации в `provider_data` или логах.

Для сохранённых карт вводим `PaymentMethod` (наш публичный идентификатор) и `ProviderToken` (внутренний токен конкретного банковского подключения). Один наш `PaymentMethod` **не гарантирует** возможность списать с карты через любой банк. Если нет совместимого токена для B, требуется новый разрешённый сценарий привязки или поддерживаемая миграция токена.

Дополнительно требуется фиксировать согласие плательщика, тип последующего платежа (CIT/MIT), основания списания, время и источник подтверждения. Т-Банк в документации различает эти сценарии через `OperationInitiatorType`.

## 11. Надёжность и производительность

**Гарантии/ограничения, заложенные в проект:**

- Сохранить операцию и ключ идемпотентности в БД **до** сетевого вызова банка.
- Вести журнал исходящих банковских команд и попыток.
- Входящие банковские события проверять криптографически, дедуплицировать и обрабатывать независимо от порядка доставки.
- Клиентские webhook отправлять по модели повторной доставки с подписанием тела и неизменным ID события.
- При неопределённом результате использовать идентификаторы операции, банковскую проверку статуса и сверку; уважать ограничения опроса ТКБ.
- Операции capture и refund защищать от гонок ограничениями сумм и блокировкой/версионированием записей.
- Настроить ограничения RPS на клиента и на банковское подключение; очередь при необходимости.
- Проводить нагрузочные испытания отдельно на публичном API и на симуляторе банков, поскольку реальный банк может иметь собственный лимит значительно ниже 100 RPS.
- Регистрировать показатели: число платежей по состояниям, задержка операций, неопределённые результаты, повторные обработки, ошибки сверки, задержка доставки webhook, загрузка соединителей.

## 12. Первые проверяемые сценарии

1. Оплата новой картой через форму банка; успешное уведомление приходит позже ответа создания.
2. Одностадийная оплата через СБП; QR истекает без оплаты; событие приходит с задержкой.
3. Холды: один окончательный полный или частичный `capture` на один холд; остаток освобождать только по доказанной семантике банка, повторный успешный `capture` запрещён.
4. Полный возврат и два частичных возврата; превышение доступной суммы отклоняется локально.
5. Привязка карты по согласию, последующий платёж без участия пользователя, удаление токена.
6. Дублирующий запрос с тем же `Idempotency-Key`, включая два параллельных обращения.
7. Тот же ключ, но изменённая сумма -> `409` без нового обращения к банку.
8. Тайм-аут банка после обработки заявки -> `processing`, уточнение, **без** оплаты через другой банк.
9. Повторное/запаздывающее/неупорядоченное событие банка -> история и суммы не искажаются.
10. Один банк недоступен до попытки -> маршрутизация через другой *только при наличии подходящего договора и способа оплаты*.
11. Банковский токен создан в ТКБ, попытка списания через другой банк без совместимого токена -> отказ маршрута/требуется перепривязка.
12. Магазин подключён к одной системе, а банк отказывает в конкретном способе оплаты -> способ скрывается в `/capabilities`.

## 14. Решения заказчика и открытые вопросы

- **BR-01 согласован 2026-10-09:** самостоятельные `Payment`, управляемые `PaymentIntent`, только покупатель инициирует новую оплату после отказа.
- **BR-02 согласован 2026-10-09:** блокировка новых попыток по сроку, лимиту попыток, отмене продавцом и рискам; финальное неуспешное состояние только при исключённом незавершённом финансовом эффекте.
- **BR-02.1 согласован 2026-10-09:** 30 минут по умолчанию (от 5 минут до 24 часов), 5 попыток по умолчанию (от 1 до 10); настройки Intent неизменны с момента создания. Покупателю — нейтральное сообщение риска, продавцу — категория и ссылка поддержки, сотрудникам с полномочиями — полные основания.
- **BR-03.1 согласован 2026-10-09:** в первом выпуске допускается одно успешное окончательное полное или частичное списание из одного холда; многократные подтверждения — отдельное расширение, пока не включено. Банковская поддержка и освобождение остатка требуют отдельной проверки.
- **BR-03.2 согласован:** при частичном окончательном списании дочернего Payment продавец передаёт `reduce=true`; сумма `amount_final` фиксируется после банковского подтверждения. Финансовый succeeded не означает отгрузку. Оставшаяся часть не собирается внутри закрытого Intent.
- BR-04 согласовано: возврат исполнен только по банковскому доказательству; неизвестность — резерв, позднее обращение — компенсирующий факт. BR-05 также согласовано: поздний успех после отмены фиксируется; автоматического Refund нет; BR-06 остаётся открытым.
- **BR-05 согласовано 2026-10-09:** при позднем успехе отмена неисполнена, Payment/Intent оплачены, магазин отдельно уведомлён; возврат только по его инициативе. Возможность авто-возврата с явным разрешением не входит в v1.
- Единый способ подключения продавцов к нескольким банкам без переоформления договоров.
- Требуется ли единая собственная платёжная страница либо используются только банковские формы.
- Параметры хранения/модели согласий для повторных списаний.
- Конкретные технологии реализации: язык программирования, БД, очередь, контейнерная платформа, количество отдельных сервисов.

## 16. BR-03.2 и NAME-01: граница предметной суммы и имена полей

- `PaymentIntent.amount` — неизменная исходная сумма покупки; `amount_final` — подтверждённая продавцом окончательная сумма; `amount_paid` — подтверждённые денежные списания до возвратов.
- Управляемый `capture` ниже исходного холда требует явного `reduce=true`; проверку делает ядро **до** банковского соединителя. Соединитель получает конкретную сумму финансовой операции и не знает, как продавец меняет стоимость покупки.
- Исходная сумма остаётся в истории; `amount_final` устанавливается после доказанного результата и закрытия неиспользованного остатка холда.
- В схемах БД используем `intent_id` как внешний ключ на намерение, `method_id` — на сохранённый метод, `amount_final` — на окончательную сумму. Не использовать в новых схемах `payment_intent_id`, `saved_payment_method_id` и `confirm_amount_reduction`.
- Конвенция NAME-01: собственные поля в API, внутренних контрактах и столбцах БД — одно смысловое слово где достаточно, два максимум. Имя дополняется описанием типа/единиц/состояний/ограничений; имена сторонних банковских протоколов передаются без изменений.
- Названия колонок БД, таблиц и индексов формально утверждаются в ходе проектирования физической модели; это не требование применить выбранную СУБД. Проектирование не должно допускать поле из трёх слов как новую норму.
