# Проект платёжного процессинга — аналитическая модель v0.1

Дата: 2026-10-08  
Статус: **проект для обсуждения, не утверждённая архитектура**  
Основа: предоставленная документация TKB PAY, официальные API Stripe, Adyen, ЮKassa, Т-Банка, Сбера и Альфа-Банка.

> Безопасность: в этом документе нет адресов закрытых банковских стендов, ключей, номеров карт или учётных данных. Коллекция Postman с учётными данными не должна попадать в репозиторий.

## 1. Входные бизнес-требования

**Подтверждено заказчиком:**

- Одна платёжная компания подключает юридические лица, ИП и физических лиц на НПД.
- Клиент принимает платежи за **собственные** товары или услуги; маркетплейсные распределения и выплаты третьим лицам не входят в начальный объём.
- Клиент подключается самостоятельно через единый кабинет без самостоятельных интеграций с банками.
- Один и тот же публичный платёжный API должен работать с несколькими банками и способами оплаты: карты, СБП, кошельки.
- Требуются: создание и получение платежа, полные и частичные возвраты, холдирование и подтверждение, привязка карт и повторные списания.
- Ориентир производительности: не менее 100 запросов в секунду на публичном API; это **не** означает подтверждённую пропускную способность каждого банка.
- Первый доступный партнёр для исследований — тестовый контур ТКБ. Правовая модель окончательно не утверждена; прямые расчёты банка с продавцом — текущая рабочая гипотеза.

## 2. Что установлено по TKB PAY

Источники — загруженные файлы `Общие+сведения+по+использования+сервиса.doc`, `Операции+платежного+шлюза.doc`, методные документы, коллекция `TKBPAY-v11042025.postman_collection.json`.

| Область | Подтверждено документацией или коллекцией | Вопрос для проверки с банком |
|---|---|---|
| Создание оплаты картой | `RegisterOrderFromUnregisteredCard`, `RegisterOrderFromRegisteredCard`, оплата через форму ТКБ | Доступ для роли агрегатора и всех торговых точек |
| Холдирование | `Hold`, `HoldWithForm`, `HoldConfirm`, `HoldReversal` | Ограничения по сроку и числу частичных подтверждений |
| Возврат и отмена | `Refund`, `Reverse` | Правила повторного возврата, асинхронные ошибки и сроки |
| Статус | `GetOrderState`; коллекция ограничивает опрос **одного платежа не чаще 1 раза в минуту** | Полный словарь банковских статусов, порядок доставки callbacks |
| Карты/токены | `BindCard`, `Unbind`, `RegisterDirectOrderFromRegisteredCard`; ID карты — `CardRefId` | Условия MIT/CIT, согласие, переносимость, сценарии повторной аутентификации |
| СБП | `SbpRegisterQR`, дополнительные `SbpCheck`, `SbpConfirm` | Какие сценарии торговой оплаты включены и правила двухэтапного СБП |
| Фискализация | `cartPositions`, `ofdParameters`, отдельные ОФД-методы | Ответственность за чеки по различным категориям продавцов |
| Безопасность | API принимает JSON через POST; HMAC-SHA1 от отправляемых байтов, заголовки `TCB-Header-Login` и `TCB-Header-Sign` | Согласовать ротацию ключей и прием callbacks |
| Подключение торговой точки | В предоставленных операциях отсутствует подтверждённый API регистрации продавца | Получить отдельный протокол onboarding/активации или уточнить ручной процесс банка |

Важно: `extId` — идентификатор операции у клиента ТКБ, `OrderId` — внутренний идентификатор TKB PAY. Наличие уникального `extId` **не доказывает автоматически идемпотентность любых финансовых вызовов**. Проверить семантику отдельно.

Также встречаются AFT, P2P, переводы, управление картами ТКБ и банковскими счетами. Это не части стартового продукта интернет-эквайринга; не экспортировать их автоматически.

**Угроза в коллекции:** в значительной части подготовительных скриптов Postman выводится секретный ключ в `console.log`. Удалить такие строки и заменить тестовый ключ.

## 4. Основные проектные принципы

1. **Один платёж — много попыток, но не более одного успешного оплачивания.** Повторная попытка возможна только когда результат предыдущей определён или доказано отсутствие финансового эффекта.
2. **Операция не равна результату.** Ответ `200` на создание возврата может означать лишь принятие заявки. Храним жизненный цикл каждого `Capture`, `Refund`, `Void` независимо.
3. **Читатель получает сохранённое внутреннее состояние, а не прямой вызов банка.** Обновление через callback, ограниченный опрос и сверку.
4. **Данные, важные для денежных обязательств, типизированы.** Нельзя держать суммы, статусы и привязки исключительно внутри произвольного BSON/JSON.
5. **Банковские детали изолированы.** Публичный API не требует банковских терминалов, EAN, `extId` ТКБ и т.д.
6. **Единая интеграция с клиентом, отдельные разрешения по банкам.** Доступный способ оплаты определяется конкретной активной банковской связью торговой точки и возможностями разрешённого терминала.
7. **Распределённая обработка не означает распределённые транзакции с банком.** Отправки и ответы записываются с восстановлением после обрывов соединения.

## 5. Предлагаемый публичный API `/v1`

| Метод | Ресурс | Назначение |
|---|---|---|
| `POST` | `/payments` | Создать платёж; `confirm: true` — инициировать сразу |
| `GET` | `/payments/{paymentId}` | Текущее сохранённое состояние и суммы |
| `GET` | `/payments` | Список с фильтрами по заказу, периоду, состоянию |
| `POST` | `/payments/{paymentId}/confirm` | Запустить подтверждение ранее созданного платежа |
| `POST` | `/payments/{paymentId}/capture` | Подтвердить полный или частичный холд |
| `POST` | `/payments/{paymentId}/cancel` | Отменить не завершённый платёж или авторизацию, если позволяет банк |
| `POST` | `/refunds` | Новый полный или частичный возврат по `payment_id` |
| `GET` | `/refunds/{refundId}` | Состояние отдельного возврата |
| `GET` | `/payments/{paymentId}/operations` | История финансовых операций (без банковских секретов) |
| `POST` | `/customers` | Покупатель в пределах конкретного магазина |
| `POST` | `/setup_sessions` | Инициировать сохранение карты без покупки |
| `GET` | `/setup_sessions/{setupId}` | Результат привязки/подтверждения |
| `GET` | `/payment_methods` | Сохранённые методы конкретного покупателя |
| `DELETE` | `/payment_methods/{paymentMethodId}` | Отключить дальнейшее использование |
| `GET` | `/capabilities` | Доступные магазину способы, функции и ограничения |
| `POST` | `/webhook_endpoints` | Настроить URL клиентских уведомлений |

На этой стадии **не** включаем публичные `payouts`, `transfers`, `split`, `balances` и прямые банковские методы. Фискализацию проектируем отдельной предметной областью с возможностью ссылаться на платёж.

### Конвенции

- `Authorization: Bearer <merchant_api_key>` — клиентский серверный ключ, с ограниченными правами и привязкой к магазину.
- `Idempotency-Key` обязателен для финансовых `POST`: уникален в пределах клиента и действия. Повтор с прежним телом даёт тот же ресурс; повтор с другим телом — `409`.
- Суммы целочисленные в младших единицах валюты: `amount.value=125000`, `currency=RUB` означает 1 250 рублей. Никогда `float`.
- Не доверять `merchant_id`, переданному в теле: определять продавца из авторизованного контекста. `outlet_id` опционален для нескольких торговых площадок одного продавца.
- `metadata` — ограниченные произвольные данные самого магазина, не содержащие карточных реквизитов и чувствительных сведений.
- Не передавать полный номер карты, CVC/CVV, банковские HMAC-ключи и данные пользовательской авторизации в публичный API. Платёжные формы и токенизацию проводит сертифицированный провайдер/банк.
- `return_url` — адрес возврата браузера; факт успешности оплаты определяем через `GET`/подписанный webhook, не по открытию этого URL. Возвратные адреса проверять по разрешённым доменам.
- Ответы на создание/изменение могут иметь промежуточное состояние `processing` и HTTP 202; это не отказ и не подтверждённый успех.

## 6. Модель состояний

Состояние `Payment` — итоговая пользовательская перспектива на одну покупку:

| `status` | Значение |
|---|---|
| `requires_payment_method` | Нужно выбрать или исправить способ оплаты |
| `requires_confirmation` | Платёж создан, но ещё не инициирован |
| `requires_action` | Плательщик должен выполнить действие: форма/3DS/СБП |
| `processing` | Исход обработки ещё не определён; сюда входит банковский тайм-аут с неизвестным результатом |
| `requires_capture` | Средства авторизованы, ожидается подтверждение холда |
| `succeeded` | Успешная оплата подтверждена по правилам соответствующего способа |
| `failed` | Отказ, новых попыток в рамках этого платежа не планируется |
| `canceled` | Платёж отменён без дальнейшего списания |
| `expired` | Срок проведения платежа истёк, отсутствие успешного финансового эффекта подтверждено |

Нельзя переводить `processing` в `failed` только из-за HTTP 500/тайм-аута банка. При неопределённости результат уточняется по банковским идентификаторам и реестрам.

**Возвраты не меняют исторический факт успешной оплаты.** `Payment.status` может оставаться `succeeded`, а `amount_refunded` увеличивается; подробности живут в `Refund`. Статусы отдельных `Capture`, `Void`, `Refund` — `pending`, `processing`, `succeeded`, `failed`.

`PaymentAttempt` хранит `initiated`, `requires_action`, `processing`, `authorized`, `captured`, `declined`, `unknown`, `failed`. Это внутренняя модель и не должна зеркально отображаться в публичный API.

## 7. Предлагаемые основные сущности

| Сущность | Назначение / существенные поля |
|---|---|
| `Merchant` | Тип `legal_entity` / `entrepreneur` / `self_employed`, юридические данные и согласованный статус |
| `Outlet` | Сайт/приложение/торговая точка внутри одного продавца |
| `AcquirerConnection` | Связь продавца/точки с банком: договор/терминал, активность, способ оплаты, правила и ограничения |
| `Customer` | Покупатель в пределах одного продавца, а не клиент нашего PSP |
| `Payment` | Наш `id`, продавец, заказ, сумма, валюта, способ, состояние, сумма авторизации/списания/возвратов |
| `PaymentAttempt` | Конкретная попытка через конкретный `AcquirerConnection`, свой ID провайдера и исход |
| `PaymentOperation` | `authorize`, `capture`, `void`, `refund` и их отдельные состояния, ссылки на оригинальную операцию |
| `PaymentMethod` | Наш долговременный идентификатор сохранённой карты/счёта, покупатель, согласие, жизненный цикл |
| `ProviderToken` | Внутренний токен банка, область применимости: банк, терминал, продавец, способ оплаты, тип договора |
| `IdempotencyRecord` | Клиент, вид действия, ключ, отпечаток запроса, связанный результат и срок хранения |
| `ProviderEvent` | Входящие банковские события (подпись/оригинальные идентификаторы/обработка и дедупликация) |
| `WebhookDelivery` | Исходящее событие клиенту, попытки доставки и проверяемая подпись |
| `SettlementRecord` | Финансовые сведения банка о перечислении продавцу — отдельно от `Payment` |
| `ReconciliationCase` | Обнаруженное расхождение: операция, суммы, причины, исправление и история |

Схема не предполагает, что каждая сущность обязана стать самостоятельным микросервисом.

## 8. Слой банковских соединителей

**Обязательные операции интерфейса (применимость определяется `capabilities`):**

```ts
interface AcquirerConnector {
  createPayment(ctx: ProviderContext, request: CreatePaymentRequest): Promise<ProviderResult>;
  getPaymentStatus(ctx: ProviderContext, reference: ProviderReference): Promise<ProviderResult>;
  capture(ctx: ProviderContext, request: CaptureRequest): Promise<ProviderResult>;
  voidAuthorization(ctx: ProviderContext, request: VoidRequest): Promise<ProviderResult>;
  refund(ctx: ProviderContext, request: RefundRequest): Promise<ProviderResult>;
  startPaymentMethodSetup?(ctx: ProviderContext, request: SetupRequest): Promise<ProviderResult>;
  chargeSavedPaymentMethod?(ctx: ProviderContext, request: SavedChargeRequest): Promise<ProviderResult>;
  validateAndParseWebhook(ctx: ProviderContext, event: RawWebhook): Promise<ProviderEvent[]>;
  fetchSettlementReport?(ctx: ProviderContext, period: DateInterval): Promise<SettlementBatch>;
}
```

`ProviderResult` — типизированное объединение: `completed`, `pending`, `requires_action`, `declined`, `uncertain` (неопределённый результат). В нём присутствуют ID попытки/операции, внешние ID, код и текст ошибки, срок/возможность повторного опроса, необязательная полезная информация для действий плательщика. **Нельзя трактовать обычный сетевой тайм-аут как `declined`.**

Конкретный соединитель имеет:

- `provider` и номер поддерживаемой версии протокола;
- схему конфигурации и связь с хранилищем секретов;
- карту внешних статусов и ошибок;
- набор возможностей: карта/СБП/кошелёк; capture, partial_capture, refund, partial_refund, card_on_file, mit, sbp_bind, и т.д.;
- параметры ограничений по запросам, окнам оплаты и срокам авторизации;
- правила проверки webhook и сверки;
- набор контрактных тестов и симуляцию ошибок.

**Способности не являются только атрибутом банка.** Они определяются как пересечение возможностей соединителя, конфигурации банковского подключения данного продавца и договора.

## 9. Расширяемые данные: JSONB или BSON

Для этих требований **не предлагаю хранить весь `Payment` в BSON**. Важные суммы, статусы, ссылки и ключи должны иметь явную схему, индексы, ограничения и транзакционную целостность.

Предложение для первой реализации: реляционное хранилище, например PostgreSQL, с полями `jsonb` (двоичный JSON). `BSON` нужен, если будет выбрана MongoDB или другой продукт, который его использует. Выбор формата JSONB/BSON — реализация, а не бизнес-требование.

Гибкие документы уместны для:

1. `AcquirerConnection.configuration` — несекретная конфигурация банка и торговой точки;
2. `PaymentAttempt.provider_data` — идентификаторы и дополнительные сведения именно этой попытки;
3. `PaymentOperation.provider_data` — ответ/состояние конкретного подтверждения, отмены или возврата;
4. `ProviderEvent.payload` — ограниченная по сроку, проверенная и очищенная копия входящего события;
5. `CapabilityProfile.parameters` — лимиты и возможность операций по действующему договору.

**Пример внутреннего документа (не внешний API):**

```json
{
  "provider": "tkb",
  "schema_version": 1,
  "connection_id": "acq_0123",
  "references": {
    "external_operation_id": "attempt-8932",
    "bank_order_id": "bank-example-431"
  },
  "context": {
    "form_flow": "bank_hosted",
    "raw_state": "BANK_SPECIFIC_CODE"
  },
  "extensions": {
    "tkb": {
      "callback_profile": "default"
    }
  }
}
```

Значения демонстрационные, это **не** фактический банковский ответ.

### Обязательные ограничения расширений

- `provider` + `schema_version`; проверка через JSON Schema, миграции между версиями.
- Публичный `metadata` (данные магазина) и внутренний `provider_data` — разные поля с разными правами доступа.
- В `provider_data` не допускаются PAN, CVC, секреты, токены доступа, исходные неподтверждённые подписи и необработанные персональные данные.
- Для конфиденциальных, но допустимых технических данных — шифрование, ограничение чтения и срока хранения; ключи и учётные данные только во внешнем хранилище секретов.
- Нельзя передавать произвольную конфигурацию напрямую в банковский запрос из API клиента: допускаются только явно описанные `payment_method_options` и разрешённые схемой параметры.
- Для поиска и сверки отдельно индексировать `provider`, `bank_order_id`, `merchant_id`, `payment_id`, `attempt_id`, `operation_id` в обычных столбцах.

## 10. Маршрутизация и токены

**Правила выбора банка:**

- доступность по договору для конкретного продавца и категории деятельности;
- поддержка конкретного платёжного инструмента и режима операции;
- ограничения по валюте, сумме, стране, MCC, условиям повторной оплаты;
- техническая доступность, ограничения частоты запросов и тарифы;
- фиксировать выбранный банк на уровне конкретной попытки.

**Запрещённое автоматическое поведение:** при тайм-ауте создания платежа в банке A нельзя автоматически создать такой же платёж в банке B, пока не исключён финансовый эффект первой попытки.

Банковские токены рассматриваются как чувствительные платёжные реквизиты: хранение в зашифрованном виде с отдельным контролем доступа, без публикации в `provider_data` или логах.

Для сохранённых карт вводим `PaymentMethod` (наш публичный идентификатор) и `ProviderToken` (внутренний токен конкретного банковского подключения). Один наш `PaymentMethod` **не гарантирует** возможность списать с карты через любой банк. Если нет совместимого токена для B, требуется новый разрешённый сценарий привязки или поддерживаемая миграция токена.

Дополнительно требуется фиксировать согласие плательщика, тип последующего платежа (CIT/MIT), основания списания, время и источник подтверждения. Т-Банк в документации различает эти сценарии через `OperationInitiatorType`.

## 11. Надёжность и производительность

**Гарантии/ограничения, заложенные в проект:**

- Сохранить намерение и ключ идемпотентности в БД **до** сетевого вызова банка.
- Вести журнал исходящих банковских команд и попыток.
- Входящие банковские события проверять криптографически, дедуплицировать и обрабатывать независимо от порядка доставки.
- Клиентские webhook отправлять по модели повторной доставки с подписанием тела и неизменным ID события.
- При неопределённом результате использовать идентификаторы операции, банковскую проверку статуса и сверку; уважать ограничения опроса ТКБ.
- Операции capture и refund защищать от гонок ограничениями сумм и блокировкой/версионированием записей.
- Настроить ограничения RPS на клиента и на банковское подключение; очередь при необходимости.
- Проводить нагрузочные испытания отдельно на публичном API и на симуляторе банков, поскольку реальный банк может иметь собственный лимит значительно ниже 100 RPS.
- Регистрировать показатели: число платежей по состояниям, задержка операций, неопределённые результаты, повторные обработки, ошибки сверки, задержка доставки webhook, загрузка соединителей.

## 12. Первые проверяемые сценарии

1. Оплата новой картой через форму банка; успешное уведомление приходит позже ответа создания.
2. Одностадийная оплата через СБП; QR истекает без оплаты; событие приходит с задержкой.
3. Холдирование, частичное подтверждение, отмена остатка в соответствии с возможностями банка.
4. Полный возврат и два частичных возврата; превышение доступной суммы отклоняется локально.
5. Привязка карты по согласию, последующий платёж без участия пользователя, удаление токена.
6. Дублирующий запрос с тем же `Idempotency-Key`, включая два параллельных обращения.
7. Тот же ключ, но изменённая сумма -> `409` без нового обращения к банку.
8. Тайм-аут банка после обработки заявки -> `processing`, уточнение, **без** оплаты через другой банк.
9. Повторное/запаздывающее/неупорядоченное событие банка -> история и суммы не искажаются.
10. Один банк недоступен до попытки -> маршрутизация через другой *только при наличии подходящего договора и способа оплаты*.
11. Банковский токен создан в ТКБ, попытка списания через другой банк без совместимого токена -> отказ маршрута/требуется перепривязка.
12. Магазин подключён к одной системе, а банк отказывает в конкретном способе оплаты -> способ скрывается в `/capabilities`.

## 13. Открытые вопросы для ТКБ

1. Существует ли отдельный договор/технический интерфейс подключения продавцов от имени платёжного агрегатора? Можно ли активировать ЮЛ, ИП и физлиц на НПД дистанционно?
2. Могут ли несколько продавцов работать через одно техническое подключение агрегатора? Как задаются и изолируются терминалы и учётные данные?
3. Есть ли формальное правило идемпотентности `extId` для каждого из финансовых методов? Как долго гарантируется уникальность?
4. Каков полный перечень статусов и кодов результата `GetOrderState`? Когда точно можно повторить вызов после неопределённого результата?
5. Какова схема подписи callbacks, повторов и получения пропущенных событий?
6. Какие сценарии сохранённых карт доступны: обычный CIT, COF MIT recurring, unscheduled, instalment? Какие ограничения по согласиям и 3DS?
7. Разрешены ли неоднократные частичные подтверждения холда? В какие сроки? Как отменяется остаток?
8. Как банк отражает возвраты, отмены, комиссии и перечисления в отчётах? Где надёжный источник сверки?
9. Какие тарифы и ограничения RPS/конкурентности на один терминал и на агрегатора?
10. Существует ли отдельная процедура для СБП: подключение продавца, терминал, QR, отмены, возвраты, повторные платежи?

## 14. Проектные решения, которые ещё НЕ согласованы

- Точная модель статусов и переходов при частичных capture/refund.
- Единый способ подключения продавцов к нескольким банкам без переоформления договоров.
- Требуется ли единая собственная платёжная страница либо используются только банковские формы.
- Параметры хранения/модели согласий для повторных списаний.
- Конкретные технологии реализации: язык программирования, БД, очередь, контейнерная платформа, количество отдельных сервисов.
- Реальные показатели доступности, задержки, RPS банка и параметры финансовой сверки.
