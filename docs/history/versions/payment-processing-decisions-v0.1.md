# Платёжный процессинг — журнал согласования требований

**Дата подготовки:** 2026-10-09  
**Версия:** 0.1  
**Статус:** проект для обсуждения; решения BR-01—BR-06 НЕ утверждены.

**Основа:** `payment-lifecycle-spec-v0.2.md`, `payment-api-v0.2.openapi.yaml`, `acquirer-connector-contract-v0.1.md`, `payment-processing-stage2-README.md`.  
Журнал не подтверждает техническую доступность методов ТКБ и не заменяет договорные проверки банка.

## 1. Как согласовываем

1. Аналитик по каждому вопросу предъявляет конкретный сценарий, предложение, альтернативу и последствия для продукта.
2. Заказчик отвечает «согласовано», «другое решение: ...» или «отложить». Молчание не означает согласования.
3. Согласованные формулировки попадают в этот журнал с датой решения, затем синхронно в спецификацию жизненного цикла и OpenAPI.
4. После закрытия решений делаем проверку противоречий между бизнес-правилами, публичным API, банковским контрактом и приёмочными сценариями. Подтверждение банком и прохождение тестов учитываются независимо от бизнес-согласования.

## 2. Уже согласованные границы продукта

| Предмет | Согласованная позиция |
|---|---|
| Продавцы | Юридические лица, ИП и физические лица на НПД |
| Назначение | Приём платежей за собственные товары и услуги, без распределения по сторонним получателям |
| Подключение | Единая дистанционная заявка и кабинет; клиент не интегрируется с каждым банком отдельно |
| Продукт | Собственный независимый платёжный API для карт, СБП, возвратов, холдов, сохранённых карт и последующих списаний |
| Банки | Несколько банков с различными протоколами; первый доступный тестовый стенд — ТКБ |
| Нагрузка | Цель — не менее 100 запросов в секунду для публичного API |

**Не утверждено:** правовая модель компании и окончательная схема перечисления выручки продавцам. Прямые расчёты банка с продавцом — рабочая гипотеза, не окончательное решение.

## 3. Бизнес-решения на согласование

### BR-01. Повторная попытка внутри одного платежа

**Статус:** ожидает решения заказчика.  
**Сценарий:** оплата заказа отклонена банком/картой; покупатель хочет выбрать другую карту.  
**Предложение аналитика:** оставить тот же `Payment` и создать новую `PaymentAttempt` после доказанного неуспеха без списания. При неизвестном результате запрещать новые попытки и смену банка до выяснения исхода. На один `Payment` — не более одного подтверждённого положительного результата.  
**Альтернатива:** всегда создавать новый `Payment` после отказа.  
**Влияние:** клиентская интеграция, количество платежей, аналитика конверсии и правила повторов.

### BR-02. Окончательная неуспешность

**Статус:** ожидает решения заказчика.  
**Сценарий:** попытки оплаты закончились либо получен окончательный отказ, не допускающий новой попытки.  
**Предложение аналитика:** `Payment.status=failed` — финальное состояние, новую попытку в том же платеже нельзя создать; для того же заказа продавец вправе создать новый `Payment`. Конкретное число попыток и сроки — отдельная политика, сейчас не фиксируются.  
**Влияние:** длительность жизни платежа, правила ограничения попыток и повторов.

### BR-03. Несколько частичных подтверждений холда

**Статус:** ожидает решения заказчика.  
**Сценарий:** из холда на 1000 ₽ магазин списывает 600 ₽ и хочет позже списать оставшиеся 400 ₽.  
**Предложение аналитика:** в первом выпуске поддержать одно полное ИЛИ одно частичное подтверждение. Не обещать многократное списание частей холда. Освобождение остатка отражать только после достоверного подтверждения банка.  
**Альтернатива:** многократные частичные подтверждения с первого выпуска, но только при банковской поддержке и дополнительных проверках.  
**Влияние:** сложность и совместимость нескольких эквайеров.

### BR-04. Когда возврат считается завершённым

**Статус:** ожидает решения заказчика.  
**Сценарий:** банк ответил HTTP 200/202 на команду возврата, но денежный результат ещё не доказан.  
**Предложение аналитика:** `Refund.status=succeeded` только при достаточном подтверждении банка; до этого отдельное промежуточное состояние. Поздняя обратная корректировка фиксируется отдельно с уведомлением магазина.  
**Влияние:** сообщения продавцу, сверка, операционные инциденты.

### BR-05. Платёж успешно завершился после запроса отмены

**Статус:** ожидает решения заказчика.  
**Сценарий:** магазин запросил отмену, но банк позднее подтвердил оплату.  
**Предложение аналитика:** не делать возврат автоматически без отдельно утверждённой политики; фиксировать подтверждённый результат и сообщать магазину, сохраняя возможность отдельного возврата. Пока отмена не доказана, не показывать `canceled` как финальный факт.  
**Альтернатива:** автоматический возврат с отдельным разрешением и ограничениями.  
**Влияние:** риск непреднамеренных возвратов и финансовых расхождений.

### BR-06. Денежные поля публичного API

**Статус:** ожидает решения заказчика.  
**Сценарий:** суммы операции, холда и возврата должны передаваться без неоднородных форматов.  
**Предложение аналитика:** для запроса `amount: 125000` и `currency: "RUB"`; в ответе `currency: "RUB"` и единый объект `amounts: {requested, authorized, captured, paid, refunded, ...}` с целыми значениями в копейках. Нет чисел с плавающей точкой; валюта одна на платёж, на старте только RUB. Комиссии не смешивать с суммами оплаты.  
**Альтернатива:** везде использовать объекты `{value, currency}` для каждого денежного поля.  
**Влияние:** контракт API и удобство разработчиков продавцов.

## 4. Отдельные проверки — не вопросы для утверждения бизнесом

**Банк и договоры:** идемпотентность операций ТКБ, идентификаторы `ExtId`, финальность `Refund`/`HoldConfirm`/`Reverse`, ограничения опроса состояния, уведомления, частичные подтверждения холда, право конкретного терминала и категории продавцов.

**Техническая реализация:** язык программирования, физическая топология, база данных, формат `jsonb`/BSON, транспорт событий, стратегия внутренних блокировок. Эти решения должны подтверждаться архитектурным анализом и испытаниями, а не приписываться заказчику.

## 5. Условия утверждения версии требований

- Каждое из BR-01—BR-06 имеет явное решение либо статус «отложено» с последствиями для первого выпуска.
- Нормы жизненного цикла, OpenAPI и банковского контракта не противоречат решениям.
- Неподтверждённые особенности ТКБ и других банков отмечены отдельно, а не выданы за факты.
- Успешная проверка на симуляторе и банковском стенде отражается как самостоятельный технический результат, не подменяемый согласованием документа.
