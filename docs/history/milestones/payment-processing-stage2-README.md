# Платёжный процессинг — материалы этапа 2

Дата: 2026-10-09. Статус: рабочие черновики, не согласованные публичные/банковские контракты.

## Согласовано заказчиком (без новых решений в этом пакете)

- Юридические лица, ИП, физлица на НПД; клиент принимает платежи за собственные товары/услуги.
- Единая дистанционная регистрация клиентов через кабинет без самостоятельных договорных подключений к каждому банку со стороны магазина.
- Собственный публичный API; несколько банков с разными протоколами; первый исследуемый стенд — ТКБ.
- Карты, СБП, привязка карт, повторные списания, холды и возвраты; масштаб от 100 RPS для публичного API.
- Способ расчётов с магазинами (напрямую через банк или через спецсчета агрегатора) пока не выбран окончательно.

## Содержимое

1. `payment-api-v0.2.openapi.yaml` — **проект** независимого публичного API. Денежные поля нормализованы: валюта платежа и однородные суммы в копейках, отдельные ресурсы операций и возвратов.
2. `acquirer-connector-contract-v0.1.md` — смысловые правила контракта банка, ответственность ядра/соединителя, безопасность, проверка результата и сопоставление с ТКБ.
3. `acquirer-connector-v0.1.ts` — типизированный интерфейс соединителя; не код работающего банковского клиента.
4. `tkb-connector-profile-v0.1.yaml` — только задокументированные методы ТКБ плюс **неподтверждённые** возможности с явным `unknown`. Не является доказательством доступа терминала.
5. `acquirer-connector-contract-tests-v0.1.yaml` — 52 тестовых сценария для будущего симулятора и разрешённых проверок на стенде. Все `not_run`.
6. `payment-lifecycle-spec-v0.2.md` — спецификация предыдущего этапа; две выявленные поправки перечислены в §3.1 документа контракта соединителя (обрабатываются как **проект** версии v0.2a).
7. `payment-processing-architecture-v0.1.md` — исходная архитектурная модель для контекста.

## Что здесь не утверждено

BR-01—BR-06 из `payment-lifecycle-spec-v0.2.md`: повторные попытки внутри одного платежа; переход в окончательный отказ; поддержка нескольких частичных подтверждений холда; критерий окончательного возврата; политика поздней оплаты после отмены; новая денежная модель API. Все внесённые изменения в API — **предложение**, а не принятое заказчиком решение.

## Проверки, которые действительно проводились

- Синтаксический разбор YAML, проверка внутренних `$ref` и уникальности операций OpenAPI.
- Проверка примеров `Payment`, `Refund` и `CreatePaymentRequest` по JSON Schema 2020-12; отрицательные проверки неоднородной суммы и отсутствия способа оплаты при `confirm=true`.
- Компиляционная проверка файла TypeScript `tsc --noEmit --strict`.
- Уникальность 52 тестовых идентификаторов, у всех статус `not_run`.
- Отсутствие значений тестового логина/секрета из приложенного окружения Postman в выходных артефактах.

Не проводились: тесты протокола ТКБ, тесты нагрузки и бизнес-сценариев, верификация прав банка/терминала, эксплуатационные проверки, независимая полная проверка OpenAPI с внешним валидатором.

## Ближайший следующий этап

1. Реализовать симулятор банка, способный воспроизводить `accepted`, `unknown`, поздние подтверждения, отказы, дубли событий и сбои после возможной отправки.
2. Исполнить 52 сценария хотя бы в части применимых к симулятору, зафиксировать наблюдаемые результаты.
3. Собрать от ТКБ официальные ответы по финальности `Refund`/`HoldConfirm`, семантике `ExtId`, идемпотентности, callback и регламенту запросов статуса.
4. После банковских подтверждений перейти к безопасным испытаниям банковского соединителя на стенде и к согласованию проекта публичного API.
