# Платёжный процессинг — комплект BR-05 / v0.9

Дата: 2026-10-09  
Статус: **BR-05 согласовано заказчиком; OpenAPI и внутренняя детализация — проект спецификации, не опубликованный контракт.**

## Решение заказчика

Запрос отмены немедленно запрещает новые попытки и конфликтующие финансовые команды, но не отменяет уже возможную банковскую отправку. `canceled` допустим только после достоверного отсутствия оплаченной суммы, действующего холда и невыясненного финансового эффекта. При подтверждённом холде процессинг пытается безопасно выполнить `void`. Если после запроса отмены банк достоверно подтвердил списание, но окончательная отмена ещё не была доказана, `Payment` и связанный `PaymentIntent` отражают **фактический успех**, запрос отмены — **неуспех**, магазин получает отдельное уведомление. **Автоматический возврат в первом выпуске отсутствует**: магазин самостоятельно создаёт `Refund`, если решит возвращать деньги. Возможность будущего явного разрешения на авто-возврат — отдельно согласуемое расширение, не текущий API. Если успех пришёл после уже доказанного `canceled`, это инцидент сверки, а не штатный переход `canceled → succeeded`.

## Предлагаемый публичный вид результата отмены

В **прямом** режиме, после позднего успешного списания:

```json
{
  "id": "pay_123",
  "status": "succeeded",
  "cancel": {
    "status": "failed",
    "reason": "payment_succeeded",
    "requested_at": "2026-10-09T10:00:00Z",
    "resolved_at": "2026-10-09T10:00:04Z"
  }
}
```

В **управляемом** режиме тот же `cancel` доступен в `PaymentIntent`, у которого `status=succeeded` и есть ссылка `paid_payment` на дочерний `Payment`.

Пример выше — **сокращённая иллюстрация** (не полный объект Payment). Полная схема содержит обязательные финансовые поля из OpenAPI.

- Событие прямого режима: `payment.cancel_failed`.
- Событие управляемого режима: `payment_intent.cancel_failed`.
- Текущий успешный платёж не даёт указания автоматически исполнить/отгрузить отменённый заказ.
- Публичный `POST .../cancel` **не принимает `refund: true`** в v1; будущую функцию не следует имитировать.

## Что именно проверено

- OpenAPI 3.1: синтаксис YAML, дублированные ключи, локальные `$ref`, уникальность `operationId`, основные примеры и новый `CancelEvent` (JSON Schema).
- NAME-01: поля схем и типизированного интерфейса — не более двух смысловых слов.
- TypeScript SPI: компиляция `tsc --noEmit --strict --target ES2020`.
- Проверочные случаи: 195 уникальных идентификаторов, все помечены `not_run`; 24 новых — для BR-05.
- ZIP: целостность и отсутствие обнаруженных тестовых секретов из предоставленного окружения.

**Не выполнено:** ни одного имитационного/банковского контрактного теста; живых запросов к ТКБ; банковского подтверждения допустимости `Reverse`/`HoldReversal`, финальности, идемпотентности или расчётных условий. Юридическая трактовка отмены договора/заказа и автоматические компенсации требуют отдельной проработки.
