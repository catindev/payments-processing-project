# BR-04 — согласование и изменения v0.8

**Дата:** 2026-10-09. **Согласовано заказчиком:** BR-01, BR-02, BR-02.1, BR-03.1, BR-03.2, BR-04 и NAME-01. **Открыто:** BR-05, BR-06 и банковская проверка финальности отдельных методов.

## Что согласовано

- `Refund` — отдельный ресурс конкретного `Payment`, без изменения `Payment.succeeded` или `PaymentIntent.succeeded` после возврата.
- `Refund.succeeded` требует *достаточного подтверждения исполнения финансового возврата* по правилам конкретного банка. HTTP 200/202 и принятие заявки — не критерий успешного исполнения.
- Доказанного исполнения достаточно для статуса `succeeded`, даже если деньги ещё не отображаются на счёте покупателя; сроки зачисления не обещаются.
- `processing` (отправка/неизвестность) и `pending` (принятие) сохраняют резерв суммы. `failed` до исполнения освобождает резерв; позднее документально подтверждённое обращение после успеха — `reversed`, неизменяемый компенсирующий финансовый факт, уведомление магазина.
- Безопасная идемпотентность при неизвестном банковском результате: старый ключ не создаёт новые банковские вызовы, новый не даёт права обойти защиту.
- Значимые webhooks: `refund.succeeded`, `refund.failed`, `refund.reversed`; допустим `refund.pending` как информационный. Дубликаты событий безопасны.

## Технические изменения

- OpenAPI добавляет уточнённую семантику `RefundStatus`, схему `RefundEvent` для уведомлений магазина, необязательные поля `completed_at` и `reversed_at` (проект полей, NAME-01), уточнения POST/GET refund. **Структура денег BR-06 не утверждена.**
- Банковский SPI расширен вариантом `ConnectorResult.kind="reversed"` только для поздней корректировки подтверждённого refund; ядро выполняет учёт, а соединитель предоставляет доказательства.
- В жизненном цикле и банковском контракте уточнены резервирование, банковские доказательства, противоречивые поздние события, корреляция нескольких возвратов.
- В YAML-каталог добавлены 24 сценария CT-148..CT-171. Это **описательные проверочные сценарии, НЕ исполненные тесты**.

## Открытые зависимости

- TKB PAY: `Refund` в Postman регистрирует заявку по `ExtId` исходного платежа; финальная семантика, уникальная идентификация отдельного refund, безопасный повтор, права терминала, поддержка частичных операций и сверки **не проверены**.
- Не утверждены: сроки зачисления, юридический момент исполнения перед покупателем, конкретные банковские таблицы, комиссии/фискализация, срок ручного расследования, поведение частичного обратного движения, автоматические повторные возвраты.
- BR-05 (поздняя оплата после отмены) и BR-06 (денежная модель) остаются открытыми.
