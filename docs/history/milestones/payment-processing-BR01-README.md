# Согласование BR-01: гибридная модель платежей

**Дата решения:** 2026-10-09  
**Версия комплекта:** 0.3-draft  
**Источник решения:** явное согласование заказчика в текущем обсуждении.  
**Статус:** BR-01 согласовано, BR-02—BR-06 открыты; банковский стенд не тестировался.

## Согласованное бизнес-правило

`Payment` — самостоятельная оплата с отдельным жизненным циклом и окончательными состояниями. Прямые интеграторы создают `Payment` сами, могут связывать их со своими заказами и отвечают за повторные оплаты.

`PaymentIntent` — **необязательная** надстройка для продавца, которому нужен один объект на покупку. Объединяет последовательные дочерние `Payment` и управляет новой оплатой после *достоверного* отказа предыдущей без финансового эффекта. Новый дочерний платёж возникает только по **новому действию покупателя**, инициированному через магазин; процессинг не переключает банк и не запускает автоматические финансовые повторы после отказа.

В `PaymentIntent` не допускаются два активных дочерних `Payment` одновременно. Неизвестный результат предшествующего платежа блокирует запуск следующего. Запрет не заменяет финансовую сверку: поздний успех внешнего банка после ранее подтверждённого отказа должен стать отдельным инцидентом.

`PaymentAttempt` как самостоятельный публичный ресурс **не вводится**. Внутренний технический журнал отправок (`DispatchIntent`) не путать с публичным `PaymentIntent`.

## Изменения API v0.2 → v0.3

| Было | Стало |
|---|---|
| `Payment` мог снова принимать другой способ после `failed` | `failed` финален, новая оплата — новый `Payment` |
| Повторный `confirm` мог создавать вторую попытку внутри того же `Payment` | `POST /v1/payments/{id}/confirm` используется только для первой инициации |
| Нет верхнего управляемого ресурса | `POST/GET /v1/payment_intents`, `GET /v1/payment_intents/{id}`, `POST .../confirm`, `POST .../cancel`, `GET .../payments` |
| `PaymentAttempt` как отдельная предметная сущность | `Payment` + банковские технические сообщения/операции |
| Только события конкретного `Payment` | Добавлены `payment_intent.*`; дочерние `payment.*` содержат `payment_intent_id` |
| Возвраты привязаны к `Payment` | Без изменений — даже у дочерних `PaymentIntent` |
| Банковский контракт содержал `payment_attempt_id` | Использует `payment_id` и `operation_id`, не зависит от `PaymentIntent` |

**Обращение внимания на финансовые суммы:** `PaymentIntent.amount_paid` — подтверждённая оплата по дочернему платежу. При финальном частичном capture она может быть меньше `PaymentIntent.amount`; магазин не должен трактовать один лишь `succeeded` как полную оплату стоимости заказа. Уточнение правил недоплаты — отдельное обсуждение вместе с BR-03.

**Идемпотентность:** повтор `PaymentIntent.confirm` с прежним ключом и телом возвращает сохранённый результат *того же исходного подтверждения и дочернего `Payment`*. За текущим агрегированным статусом после следующих действий нужно обращаться к `GET /v1/payment_intents/{id}`. Параллельные подтверждения с разными ключами допускают создание только одного дочернего платежа.

## Не согласовано этим решением

- BR-02: лимиты повторных покупательских оплат, срок жизни `PaymentIntent`, финальное `failed` / `expired` у намерения.
- BR-03: последовательные частичные capture и поведение намерения при `amount_paid < amount`.
- BR-04: доказательство окончательного успеха возврата.
- BR-05: поздний успех оплаты после отмены и политика компенсаций.
- BR-06: форма денежных полей публичного API. В v0.3 используется **предложенный**, не утверждённый формат.
- Дополнительно: уникальность `order_id` между прямыми платежами и разными намерениями; достоверная проверка действия покупателя на стороне сервера; реальные банковские возможности ТКБ.

## Проверки и границы достоверности

- Файлы YAML разобраны, внутренние ссылки OpenAPI проверены, примеры основных объектов и запросов проверены JSON Schema 2020-12.
- Контракт TypeScript компилируется `tsc --noEmit --strict`.
- 77 сценариев имеют уникальные ID и статус `not_run`.
- Действующие значения учётных данных из переданного окружения Postman в новые файлы не перенесены.

Не выполнялись: реальные API-запросы в ТКБ, нагрузочные испытания, симуляция переходов в работающем коде, внешняя полноценная валидация OpenAPI. Материалы — контракт на проектирование, а не отчёт об исполнении тестов.
