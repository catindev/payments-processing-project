# Платёжная форма нового процессинга: ревью трёх архивов и исследование рынка

**Дата:** 9 октября 2026 года.  
**Статус:** экспертное исследование; не согласованное техническое задание и не отчёт о проведённом PCI DSS-аудите.  
**Основа:** `pyment-form-main.zip`, `3ds-fronend-main.zip`, `payform_rest-develop.zip`, проект BR-07 (Checkout), действующие согласования BR-01—BR-06 и NAME-01.

## 1. Итог

**Рекомендуемая продуктовая модель:** один общий Checkout на нашем домене с минималистичным UX и темой из **одного акцентного цвета**, единым отображением карт/СБП, собственной страницей результата и независимым от банка платёжным ядром. Способ сбора данных карты выбирается отдельно по поддержке банка и готовности защищённого контура: `hosted`/redirect, безопасные `hosted fields`/провайдерская токенизация (при наличии), собственный PCI-контур для WOF/direct. В первом выпуске не считать WOF разрешённым без подтверждения банка и требований PCI.

По исходникам:

- **Старую форму** использовать как **референс визуального языка**, а не готовое приложение и не готовый защищённый интерфейс.
- **Старый 3DS-фронтенд** использовать как **каталог банковских сценариев браузерных переходов**, но не как самостоятельное обязательное приложение: новую реализацию проектировать как браузерные действия, выдаваемые серверной оркестрацией 3DS.
- **Форму ТКБ** использовать как **функциональный референс, каталог сценариев, набора полей и тестов**. Не копировать модель с десятками независимых React-компонентов под каждого партнёра, иначе сопровождение сотен мерчантов станет дорогим.

Главное отличие собственного Checkout от самостоятельного Payment Core — UI не должен хранить или решать финансовые состояния самостоятельно: успешный возврат браузера, завершение 3DS и QR не являются достаточными доказательствами оплаты. Единственный источник — проверенный результат банка, отражённый в `Payment` / `PaymentIntent`.

## 4. `3ds-fronend-main`: зачем, вероятнее всего, выделяли в приложение

`src/App.js` читает идентификатор из URL, делает `GET /core/v1/public/3ds?id=...`, получает `gateway_id` и `tds_data`, затем выбирает механизм перехода:

- шлюзы с готовым `redirect_url` — переход браузера;
- некоторые шлюзы — скрытая POST-форма с `creq` и `threeDSSessionData` (3DS2);
- некоторые — POST `PaReq`, `MD`, `TermUrl` (3DS1);
- другие варианты добавляют параметр терминального callback URL.

По коду присутствуют интеграционные ветки для нескольких провайдеров (встречаются Smartpay, Монета, Евраз, Халык, Алтын, Apex, Paygine, БЦК). Это объясняет выделение независимого приложения: **отдельная общая точка браузерных POST-переходов**, которая могла запускаться по статусу `150` независимо от страницы ввода карты и интеграции банка. Документированная исходная мотивация в README отсутствует — это реконструкция по исходникам, не установленный факт.

**Важно:** это не самостоятельный полноценный 3DS Server и не ACS. Он не принимает решения об аутентификации, а пересылает браузер с нужными параметрами.

### Что переиспользовать

- Каталог поддерживаемых вариантов `redirect`, `form_post`, `creq`, `PaReq/MD/TermUrl`.
- Поддержку POST-переходов, которых нельзя заменить обычным GET-редиректом.
- Отделение браузерного действия от серверного решения о финансовом результате.

### Что изменить

- Убрать `gateway_id`-switch из браузера. Банковский соединитель возвращает **нормализованное браузерное действие** с ограниченным набором параметров; Checkout UI исполняет его. Точные имена `creq`, `PaReq`, `MD` могут сохраняться только в bank-specific действии.
- Проверять назначение POST/redirect, срок жизни и корреляцию 3DS-сеанса; не доверять произвольному `action` URL.
- Исключить вывод чувствительных параметров в консоль: `PostRedirect.js:12,22`, `PostRedirectAltyn.js:17`, `PostRedirectApex.js:12–16`, `PostRedirectHalyk.js:12`, `PostRedirectBccAft.js:12,24`.
- Не делать redirect из тела рендера React (`App.js:48–50`).
- Не считать возврат из ACS доказательством оплаты. Сервер завершает аутентификацию у банка и проверяет оплату.
- Вместо обязательного отдельного SPA рекомендован переиспользуемый модуль `3DS Action Runner` внутри нашего Checkout. Отдельный origin / микрофронтенд допустим, если границы безопасности и процессинг это оправдают; *отдельный репозиторий не является функциональным требованием*.

## 5. `payform_rest-develop`: что представляет собой проект

Это зрелая многосценарная форма на React/TS. Архитектура отчасти соответствует Feature-Sliced Design (README), но физически содержит много отдельных визуальных реализаций.

### 5.1. Уже решённые задачи

- `src/app/router/router.tsx`: единая страница по `/:id`, отдельный результат и ошибка.
- `src/hooks/use-init-app.tsx`, `src/api/fetch-token.ts`, `src/api/fetch-status.ts`: выдача доступа к checkout-сеансу, получение состояния, опрос и получение 3DS-данных.
- `src/hooks/use-pay-form.ts`: управляемая форма карты; маска, валидация, сохранённые карты, определение платёжной системы, отображение комиссии.
- Операции по `operationType`: `pay`, `bind`, `bindlite`, `bindNoSum`, `cardToCard`, `refill` (`src/components/home/home.utils.ts`). Последние два **не входят** в ранее согласованную область нашего первого выпуска и не должны попадать в checkout автоматически.
- `src/shared/utils/3ds.ts`: браузерные POST-формы, скрытые iframe 3DS Method, challenge-переходы; поддержка разных версий/вендорских вариантов.
- `src/partners-ui`: 38 каталогов партнёрских реализаций. `formAlias` приходит в `merchant`, после чего маппинг лениво загружает конкретную форму (`src/components/home/constants/pay-form.tsx`).
- `tests/e2e`, `tests/visual`: проверки валидации и эталонные скриншоты. Это полезная база для будущих тестов, но тесты завязаны на ТКБ API и UI.

### 5.2. Архитектурные минусы для нашего продукта

- Из 17 907 строк TS/JS в `src` около 13 994 находятся в партнёрских `.tsx` компонентах; это оценка по подсчёту строк, а не уникальности логики. **При расширении на сотни мерчантов копирование формы под каждого партнёра нецелесообразно.** Лучше 1–3 UX-шаблона с конфигурацией темы и включаемых секций.
- Приложение поддерживает больше финансовых продуктов, чем сейчас требуется нашему Checkout. Нельзя переносить `cardToCard`/`refill` без нового бизнес-решения и правовой проверки.
- Обработчики 3DS и опрос смешаны с frontend-состояниями. В новой архитектуре банковский маршрут/события определяет сервер, frontend — действие покупателя и отображение состояния.

### 5.3. Конкретные риски в исходниках (статический анализ; не заявление о работающей production-инсталляции)

**P0 при включённой телеметрии: PAN в запросах и логах.**

- `src/hooks/use-quote-info.ts:66,71–75`: `shouldFetch` фактически истинно при **любых** `number.length >= 6`; передаётся `number`, а не ограниченный BIN.
- `src/api/quote-info.ts:5–7`: запрос `GET .../quote?bin=${cardNumber}` может содержать полный PAN в URL. URL часто попадает в access logs, прокси, APM, историю мониторинга. Требуется передавать лишь разрешённый BIN (6 или 8 цифр по требованиям интеграции), а лучше согласовать безопасный интерфейс с карточным контуром.
- `src/hooks/use-quote-info.ts:27–29,71–74`: сообщения в Faro содержат **полный введённый номер карты**, если сбор включён. Это не гипотетическая строка-комментарий, а исполняемый код. **Считать блокером до исправления.**

**Высокий риск при неверной конфигурации аналитики:**

- `src/app/index.tsx:14–23`: Faro и инструментирование с `captureConsole: true`.
- `src/app/index.tsx:26–39`: OpenReplay с `capturePayload: true`, `captureInIframes: true`. Нужны ограничения по endpoint'ам, исключение сетевых тел оплат и 3DS, маскирование всех платёжных полей и проверка SDK. В приложенной `.env` соответствующие функции выключены; это не подтверждает их настройки в реальном production.

**Другие вопросы безопасности/надёжности:**

- `src/hooks/use-init-app.tsx:67–71,119,145`: браузерный access token сохраняется в `localStorage`; возможна кража при XSS. Новый checkout лучше проектировать с короткоживущими токенами, ограниченными ресурсом и правом на действие; способ хранения оценивать отдельно с CSP и threat model.
- `src/hooks/use-init-app.tsx:248,254`: в одном сравнении используется `threeDSServerTransID`, а далее `threeDSServerTransId` — потенциальное расхождение регистра в 3DS2-сценарии, нужно тестировать по реальному контракту.
- `src/hooks/use-payment-status-polling.ts:30–32,139–145`: опрос каждую 1 с, потом 5 с. Он может быть допустим при **запросе нашего кэша** состояния, но **не должен напрямую превращаться в такой же опрос банка** (по документам ТКБ GetOrderState есть ограничение на частоту опроса).
- `src/components/home/home.tsx:38–45`: браузерный redirect при окончательном статусе по URL от merchant. Нужна доверенная привязка URL к заказу и мерчанту и allowlist.
- React-компоненты получают PAN/CVC и передают их через `cardsInfoRequest` на backend (`src/hooks/use-pay-form.ts:96–123`, `src/shared/types/form.ts:35–39`). В новом процессинге это возможно **только через утверждённый PCI card gateway**, не через Core и общий API продавца.
- `src/shared/schemas/payform.schemas.ts` допускает CVC строго из 3 цифр; уточнить список карт и форматов для рынка запуска.

Качество / безопасность ни одного из трёх приложений **не подтверждено запуском тестов, внешним пентестом или сертификацией**.

## 7. Как предлагаю устроить новый Checkout

```text
Merchant Backend  ──────> Payment API ──────> Payment Core
       │                   │                     │
       │                   └─ checkout session   ├─ Payment / Intent / Operations
       │                                          ├─ routing / idempotency / ledger
       └── checkout.url ──> Checkout UI <───> Checkout Backend
                                     │
                             select payment method
                             ├─ card: bank-hosted redirect
                             ├─ card: hosted-fields/token (when available)
                             ├─ card: PCI Card Gateway -> bank WOF/direct
                             └─ SBP: QR/link on our page
                                  │
                             3DS Action Runner when required
                                  │
                          Bank events / status / reconciliation
                                  │
                          Payment Core final status -> UI & webhook
```

### 7.1. Слои и границы

1. **Checkout UI:** визуальные компоненты, суммы, мерчант, выбор способов, СБП, карточные поля только в безопасном режиме, 3DS browser action, состояние и страница результата. Форма визуально наша независимо от того, у какого банка прошла оплата.
2. **Checkout Backend:** ограниченный checkout session (привязан к merchant+resource+TTL); право начать оплату после действия покупателя. Не отдавать merchant API keys в браузер; проверять allowlist return URL.
3. **Payment Core:** `Payment`, `PaymentIntent`, операция и банковский источник истины; один активный дочерний Payment, блокировка при `unknown`, соблюдение согласованных 30 мин / 5 попыток и банковских ограничений.
4. **Bank Connector:** операции и подтверждённые возможности `(merchant, terminal, method, mode)`. Выбор `hosted`/`direct` и 3DS action; запрет fallback после потенциальной отправки финкоманды до установления исхода.
5. **PCI Card Gateway:** при прямом API или поставщике токенизации — строго ограниченная обработка карточных данных, отдельные секреты, мониторинг, сертификация и строгая политика логирования. **Никакого PAN/CVC в платёжном ядре**, журнале, API продавцов и бизнес-событиях.

### 7.2. Варианты представления UI

Для первого выпуска: полноэкранная адаптивная страница на нашем домене (`checkout.url`), которую магазин может открыть редиректом. Для будущего: pop-up/iframe/embed через официальный JS SDK и строгую CSP/frame policy, без выдачи карточных данных магазину. Встраивание банковского iframe возможно только по официальным условиям банка и с учётом browser compatibility.

### 7.3. Тема мерчанта

Предложение JSON-конфигурации, **не согласованная версия API**:

```json
{
  "theme": {
    "accent": "#6752D6",
    "logo": "https://assets.example.invalid/merchant/logo.svg",
    "mode": "light"
  }
}
```

- В начале разрешить **только** `theme.accent` и, по желанию, логотип из нашего доверенного asset-хранилища. Не разрешать мерчанту поставлять произвольный CSS/JavaScript, URL произвольных скриптов, CSS-ключи и типографику.
- Контраст, hover/focus, borders, success/danger/disabled, QR и фон считаются из нейтральной системной палитры и проверяемых правил доступности; **цвет ошибки — семантический, а не просто затемнение акцента**.
- Контраст текста минимум по принятому продуктом стандарту WCAG; не считать все 24-битные цвета допустимыми без проверки.
- Снимок темы хранить в checkout-сеансе. Не наследовать чужую тему из `localStorage`. Важно отделить тему от банка/route (смена эквайера не перекрашивает форму без решения мерчанта).
- На первом этапе не добавлять свободный редактор композиции: можно позже расширить `theme` контролируемыми атрибутами, не ломая семантику.

### 7.4. Браузерные действия после выбора способа

Общий тип `next_action` (нейтрально к банку) должен различать `redirect`, `post`, `3ds_method`, `3ds_challenge`, `display_qr`, `poll_wait`, `done`. У банков могут отличаться параметры POST, но браузерный модуль должен принимать **подписанный/привязанный к checkout session объект**, а не произвольные URL с query-string. Платёжные статусы определяются сервером, browser callbacks не доверенные.

## 8. Безопасность и соответствие требованиям PCI

PCI SSC различает модели, где вся карточная страница размещается у сертифицированного провайдера, и прямую сборку web-формы мерчантом; область PCI зависит от **фактического пути данных и ролей организации**. Для нашей компании, выступающей процессингом/сервис-провайдером, нельзя автоматически применять категорию или SAQ небольшого мерчанта. Окончательную программу подтверждает эквайер, платёжные системы и квалифицированный QSA. Источники:

- https://www.pcisecuritystandards.org/faqs/if-a-merchant-s-e-commerce-implementation-meets-the-criteria-that-all-elements-of-payment-pages-originate-from-a-pci-dss-compliant-service-provider-is-the-merchant-eligible-to-complete-saq-a-or-saq-a-ep/
- https://www.pcisecuritystandards.org/faqs/1291/
- https://www.pcisecuritystandards.org/faqs/1319/
- https://blog.pcisecuritystandards.org/new-information-supplement-payment-page-security-and-preventing-e-skimming

**Стоп-факторы для прямого WOF:** неизвестные требования к платформе; не подтверждены права банковского терминала и 3DS сценарии; PAN/CVC в URL/логах/телеметрии; не проверен доступ сторонних скриптов/систем воспроизведения сессий к карточному DOM. Проверить SDK и телеметрию до любых live данных. PCI SSC отдельно запрещает хранение CVV после авторизации, даже в шифрованном виде.

## 9. План реализации и закрытия требований

| Этап | Пакет работ | Проверяемый результат |
|---|---|---|
| A — продукт | Согласовать BR-07: platform-hosted checkout URL обязателен; одна цветовая тема; redirect банка; card hosted/direct только по подтверждённой возможности | Подписанное бизнес-решение |
| B — reuse | Извлечь UX-компоненты, сценарии 3DS, визуальные эталоны Playwright и отказные сценарии из старых проектов | Каталог экранов и набор тестовых случаев |
| C — банковский контракт | Направить ТКБ перечень WOF, 3DS2, PCI/терминалов, отзывов, hosted fields/token; проверить sandbox | Матрица подтверждённых возможностей ТКБ с evidence |
| D — безопасность | Определить PCI boundary, threat model, скрипты, CSP, redirection URL, session/telemetry design | Подтверждённые меры и владельцы рисков |
| E — Checkout v1 | React+TS, одна theme, PaymentIntent/Payment, QR, hosted redirect, результат и статусы | Запускаемый и тестируемый checkout, visual/accessibility/E2E |
| F — WOF direct | PCI Card Gateway, 3DS2-цепочка, bank connector, fallback до отправки, contract tests | Банк подтверждает WOF, продовые допуски и E2E |

**Не делать до согласования:** копировать код банковской формы вместе с внутренними SDK; направлять PAN/CVC в Payment Core; оставлять debug/telemetry PAN; генерировать любые банковские WOF возможности из одного присутствия endpoint; считать UI-возврат подтверждением списания; объединять карточные формы нескольких мерчантов общим localStorage.

## 10. Решения, которые надо принять

1. BR-07: первый выпуск **допускается** без собственного серверного WOF при наличии нашей брендированной страницы, СБП и безопасного банковского hosted-перехода, либо WOF — безусловный блокер первого выпуска?
2. Начальный интеграционный UX: `checkout.url` (redirect) обязателен; embedded JS modal/iframe отложить или включить сразу?
3. Параметры темы: **только один `accent`** в кабинете в первом выпуске, логотип/название из уже проверенного профиля мерчанта? (Предлагается: да.)
4. Кто и на каком основании будет оператором карточных данных и владельцем PCI/QSA-проекта? Без этого нельзя допускать прямое WOF к production.

## 11. Точечные вопросы к ТКБ

1. Какие WOF/direct/3DS2 и hosted методы доступны **нашему терминалу и договорному статусу**? Действует ли это для юрлиц, ИП и НПД?
2. Есть ли публичный/партнёрский JavaScript SDK для **браузерной токенизации**, защищённых `hosted fields` или передачи криптограммы без нашего серверного PAN?
3. Подтверждённые требования к PCI DSS, 3DS Server/ACS и сертификации маршрутов WOF; кто владелец внедрения 3DS2?
4. Точные контракты `3ds2check/storecard`, `3ds2Authenticate`, validate/finish, кодов ошибок и финального ответа.
5. Возможность отключения собственной банковской формы на конкретном терминале и использование WOF на собственной Checkout-странице.
6. Правила авторизации/идемпотентности/TTL/получения состояния, реальные тестовые сценарии отказов, повторов и тайм-аутов.
7. Поддерживается ли перенос существующего токена карты между терминалами/банками? Если нет — не обещать его.
