# Вопросы к ТКБ по банковским API (до полноценного WOF-теста)

1. Предоставлено ли нашему конкретному торговому терминалу право на WOF-card debit, WOF-hold и привязку карты? Отдельные тарифы, договоры или банковские роли?
2. Какие методы и URL актуальны для 3DS 2.0 и каковы точные request/response payloads? Какие поля поступают ACS и кто принимает browser return/challenge?
3. Какие тестовые карты и тестовые результаты (frictionless, challenge success, challenge fail, decline) можно использовать без риска реального списания?
4. Каков достоверный источник финального результата debit/hold/capture/void/refund/reverse: synchronous reply, authenticated notification, status query, registry? Подтверждается ли подлинность callback?
5. Можно ли безопасно отправить тот же запрос по исходному `ExtId` после timeout? Какова идемпотентность **по каждому методу**?
6. `not_found` по `GetOrderState` — окончательный признак отсутствия списания или временное отсутствие? Минимальный интервал запросов состояния?
7. Какие банковские идентификаторы отдельных `Refund` / `Capture` / `Void` доступны? Как отличить два частичных возврата одного платежа?
8. Есть ли поддержка hosted fields, SDK и браузерной токенизации, при которой наша форма остаётся собственным UX без прохождения PAN/CVV через наш сервер?
9. Какие PCI DSS и 3DS проверки/аттестации требуются для такого вида merchant-form интеграции? Допустимые TLS/origin/whitelist, iframe/redirect/callback?
10. Как ведут себя `Reverse` и `Refund` при позднем банковском успехе после запроса отмены? Что можно делать до/после клиринга?
11. Когда подтверждается освобождение остатков после частичного capture, какое окончательное состояние исходной авторизации? Поддерживаются ли несколько capture или refunds на нашем терминале?
12. Какие реестры, settlement данные и механизмы сверки доступны компании с выбранной юридической ролью агрегатора?

Примечание: наличие WOF/3DS эндпойнтов подтверждено переданными материалами, но ответов на эти вопросы в наших испытаниях пока нет.
