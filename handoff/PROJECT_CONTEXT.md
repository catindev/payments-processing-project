# Контекст проекта для нового агента / новой сессии

## Участники

- **Владелец продукта:** принимает бизнес-решения, предоставляет доступы к тестовым стендам и исходным материалам.
- **ChatGPT (системный аналитик):** ведёт согласование, анализ архитектуры, критический аудит, проектные контракты и интерпретацию результатов.
- **Локальный Codex/Claude:** проверяет реализуемость, запускает только разрешённые безопасные тесты, создаёт воспроизводимые отчёты, вносит код/исправления через PR.

## Задача

Проект независимого мультибанковского платёжного процессинга/агрегатора для юрлиц, ИП и физлиц на НПД, продающих **собственные** товары и услуги (не marketplace/split). Единый merchant API, дистанционное подключение, карты, СБП, дальнейшее расширение на кошельки, холдирование, capture, возвраты, сохранённые карты и последующие списания. Целевая нагрузка на **публичный API** >=100 RPS, не на банковский API. Первый исследуемый банк — TKB PAY.

## Уже согласовано

- **BR-01:** `Payment` самостоятельный и финальный; `PaymentIntent` опционально объединяет последовательные дочерние `Payment`. Повтор только по действию покупателя. При `unknown` нельзя запускать другую оплату в том же Intent.
- **BR-02 / 02.1:** комбинированное закрытие намерения по времени/попыткам/отмене/риску. По умолчанию 30 минут (5 минут–24 часа), пять попыток (1–10). Снимок настроек на создание. Финальное неуспешное состояние только при исключении финансовых эффектов. Многоуровневое раскрытие риска.
- **BR-03.1:** по одному холду одно окончательное полное или частичное списание в первом выпуске; multicapture позже.
- **BR-03.2:** подтверждённое уменьшение суммы Intent при частичном финальном capture; сохранять запрошенную/final/paid сумму; `reduce` как лаконичное имя.
- **BR-04:** `Refund.succeeded` только по достаточному банковскому доказательству; неизвестное состояние/позднее обращение обрабатываются раздельно.
- **BR-05:** поздняя успешная оплата после запроса отмены = успех оплаты + неуспех отмены + уведомление магазина. Автовозврата в v1 нет.
- **BR-06:** суммы целыми минимальными единицами валюты, по платёжному объекту одна `currency`, на старте RUB и копейки; `amounts` в ответах. Комиссии отдельно.
- **NAME-01:** собственные поля 1 слово, максимум 2.
- **BR-07:** собственная карточная форма с **реальным вводом** PAN, срока и CVV в нашем UX — обязательная функция продукта. При разрешённом WOF/API direct использовать её, банковская форма — fallback. Брендирование одним accent-цветом, общий Checkout для карты и СБП. ACS для 3DS может быть внешним. PAN/CVV запрещены вне специального PCI-контура. Первичный кандидат — TKB PAY, права не проверены.

Нормативные тонкости см. в `docs/current/payment-processing-decisions-v1.1.md`, не полагайся только на этот обзор.

## Открыто и не согласовано как факт

- Окончательная **правовая модель** агрегатора и схема перечисления денег продавцам; прямые выплаты банка — лишь гипотеза.
- Право нашего конкретного банковского терминала использовать WOF, результаты 3DS2, безопасная идемпотентность и финальные банковские статусы.
- Область и оценка PCI DSS, кто аттестует, сколько это будет стоить/занимать.
- Полная работоспособность payment core, исходящие webhooks, сверка и 100 RPS ещё **не доказаны**.
- Точная политика маршрутизации банков, состав SDK/способ встраивания Checkout и условия отдельных терминалов.
- Старые frontend-архивы были рассмотрены на уровне кода, но не добавлены в этот handoff как лицензируемые собственные материалы. Результат ревью в `docs/research/checkout-forms-comparative-review-v1.md`.
