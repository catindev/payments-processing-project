# Инструкция техническому агенту (Codex / Claude и другим)

## Роль и источники истины

Ты инженер-исследователь и исполнитель экспериментов **в поддержку** системного аналитика и владельца продукта. Не выдавай гипотезы за проверенные факты. Не принимай новые бизнес-решения от имени владельца.

**Приоритет источников:**
1. `docs/current/payment-processing-decisions-v1.1.md` и `docs/current/payment-naming-conventions-v1.1.md` — согласованные продуктовые нормы.
2. `docs/current/payment-checkout-design-v0.2.md` и `docs/current/payment-lifecycle-spec-v0.12.md` — проектные технические подробности, где ещё могут быть вопросы.
3. `docs/current/payment-api-v0.12.openapi.yaml`, `acquirer-connector-v0.6.ts`, банковский профиль — проект контрактов и неподтверждённые банковские возможности.
4. `docs/research/` — аналитика; `docs/history/` — история, не источник актуальных требований.

При противоречии **не исправляй бизнес-правило молча**: запиши `docs/changes/` RFC/issue, укажи источник, предложи варианты. Исправления типовых ошибок, тестов и явно неверных ссылок допустимы через отдельный PR.

## Формат работы

- Работай по заданиям `tasks/`, сохраняй рабочую ветку `research/<scope>` или `fix/<scope>`; выполняй только действия, на которые дал право владелец в тестовом окружении. Если разрешённый sandbox scope уже зафиксирован в контексте, не запрашивай отдельное подтверждение для каждого read-only диагностического запроса.
- Перед экспериментом фиксируй гипотезу, разрешение, окружение, предусловия, шаги, ожидаемое поведение и безопасный способ отката.
- Каждую проверку отмечай `PASS / FAIL / BLOCKED / NOT_RUN / INCONCLUSIVE` с датой, ревизией и очищенными свидетельствами. **Ни одна проверка не считается выполненной по наличию YAML-сценария.**
- Отделяй наблюдение (ответ банка) от интерпретации (значит ли это финальное списание/возврат). Формулировка «банк поддерживает» допустима только для конкретного метода, терминала, типа операции и условий, если есть доказательство.
- Публикуй отчёт и изменения в отдельной ветке, предлагай PR. Не делай push в `main` и не перезаписывай `docs/current/` без явного согласования.
- Соблюдай NAME-01: название *нашего* поля 1 смысловое слово, если достаточно; максимум 2. Внешние имена банка не переименовываются на wire.

## Безопасность — обязательные запреты

- **Не выполняй реальные финансовые операции** и не обращайся к production без явной авторизации. Только заранее разрешённый bank sandbox, тестовые карты/операции.
- Не используй настоящий PAN/CVV. Не публикуй действующие credentials, приватные ключи, PAN/CVV, session/access tokens или неочищенные токены в Git, общих логах, трассировках и публичных отчётах.
- Не используй чужие банковские исходники и приватную документацию вне прав, предоставленных владельцем; не публикуй их.
- Не переносить диагностические скрипты Postman, способные печатать секреты, в тесты без очистки.
- Не повторяй денежный вызов после неизвестного результата без документированной идемпотентности именно этого метода либо доказанного отсутствия первоначальной отправки.
- Не обходи 3DS, антифрод, сертификацию или банковские условия ради прохождения теста.
- Не создавай PCI-ready заявления на основании локального теста; необходим независимый формальный scope/assessment и согласование эквайера.

## Sandbox diagnostics: три отдельных канала

Это проектная политика для **ранее разрешённого sandbox scope**, не новый допуск к финансовым операциям. Она не отменяет исторические разрешения на test-only fixtures и тесты и не переписывает их результаты, включая `UNKNOWN`.

1. **Local diagnostics.** Полный фактический response разрешено читать, анализировать локально и сохранять вне репозитория/Git по уже данному owner scope, без дополнительных запросов разрешения на каждое чтение или сохранение. Обычный режим — plain response JSON с owner-only доступом (каталог `0700`, файл `0600`). AES-GCM, access log и TTL — независимые opt-in опции protected mode, не предусловия диагностики; 24 часа — лишь возможное значение TTL. Raw не отправляется автоматически в общие tool logs.
2. **LLM context.** Агенту доступен полный структурированный диагностический ответ после адресного удаления известных auth secrets, configured login/secret, приватных ключей, CVV и PAN, session/access tokens, включая их вхождения в строки ошибок, заголовки и URL. Сохраняй остальную структуру, значения, неизвестные поля и error messages: они сами по себе не секрет. Sanitization не означает whitelist, сведение к категориям или отказ модели в анализе полного ответа; hashes/types/lengths допустимы как дополнение, не замена диагностике.
3. **Public Git / отчёты в репозитории.** Отдельный review обязателен перед включением диагностических данных в Git или публичный отчёт: очистка для LLM не равна разрешению публикации. Проверяй секреты, приватные банковские материалы и право публикации; автоматического экспорта local response/LLM context в Git нет. Raw artifacts, ключи и local access log остаются вне репозитория.

Сначала прочитай фактический response локально и его полноценную очищенную структуру, затем делай выводы. Не объявляй `BLOCKED` только из-за неизвестных полей/error messages; недостаточность доказательства результата — `INCONCLUSIVE`, а неизвестный денежный эффект остаётся `UNKNOWN` и блокирует денежный повтор, не диагностику. Если действительно есть ограничение, назови его источник: `protocol / tool / project / environment / security risk`, конкретное условие и свидетельство; не выдумывай запрет raw chat от «higher policy».

План CLI и неизменяемые financial gates — в [EXECUTION_PROTOCOL](<handoff/EXECUTION_PROTOCOL.md>) и [RFC-002](<docs/changes/RFC-002-sandbox-raw-reconciliation.md>). Это требования/план, не заявление о готовности кода.

## Отчётность

Заполняй [шаблон эксперимента](<reports/templates/experiment.md>); в `reports/results/<scope>/` включай только отдельно reviewed test-only доказательства. Полную local диагностику храни вне репозитория; в отчёте укажи безопасную ссылку/идентификатор и состояние public review без секретов. В финале указывай, какие требования **подтверждены**, **опровергнуты**, **блокированы** и **ещё не проверены**, с прямыми путями к материалам. Коммиты и PR должны быть воспроизводимыми.
